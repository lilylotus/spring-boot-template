# Spec Delta

## Purpose

定义网关对下游服务的故障隔离行为：什么情况下停止向下游转发、每秒最多放行多少请求、以及被拦下的请求会收到什么样的响应。目标是让下游故障或过载就地收敛在网关，而不是把压力继续传导给下游、把等待传导给调用方。

## ADDED Requirements

### Requirement: /proxy 路由的熔断保护

网关 SHALL 统计经 `/proxy/**` 转发到 `BootDemo` 的调用结果，当失败率超过阈值时打开熔断，在熔断打开期间 MUST 直接返回降级响应而不再向下游发起请求。熔断 MUST 在冷却一段时间后进入半开状态试探性放行少量请求：试探成功则关闭熔断恢复转发，试探失败则重新打开。

统计口径 MUST 包含下游连接失败、下游超时、以及下游返回的 5xx 响应；4xx 响应是调用方的问题，MUST NOT 计入失败率。

#### Scenario: 下游持续失败后熔断打开

- **WHEN** `BootDemo` 连续返回 5xx 或连接失败，失败率超过配置阈值且已达到最小样本数
- **THEN** 熔断打开，后续 `/proxy/**` 请求立刻收到 `503` 降级响应，网关不再向 `BootDemo` 发起任何请求

#### Scenario: 熔断打开期间不穿透到下游

- **WHEN** 熔断处于打开状态，客户端请求 `GET /proxy/welcome`
- **THEN** 网关在不接触 `BootDemo` 的前提下返回 `503`，且 `BootDemo` 侧不产生该请求的访问日志

#### Scenario: 冷却后半开并恢复

- **WHEN** 熔断打开满配置的冷却时长，`BootDemo` 已恢复正常，试探请求成功
- **THEN** 熔断关闭，`/proxy/**` 恢复正常转发

#### Scenario: 半开试探失败则重新打开

- **WHEN** 熔断进入半开状态，试探请求仍然失败
- **THEN** 熔断重新打开，并重新开始计算冷却时长

#### Scenario: 下游 4xx 不触发熔断

- **WHEN** `BootDemo` 持续返回 `404`，且这是唯一的失败来源
- **THEN** 熔断保持关闭，`404` 原样返回给调用方

### Requirement: /proxy 路由的请求限流

网关 SHALL 对 `/proxy/**` 施加每秒请求数配额，配额由整条路由的所有调用方共享，不按调用方身份区分。超出配额的请求 MUST 立即被拒绝并返回降级响应，MUST NOT 排队等待配额释放（排队会占住事件循环线程）。配额 MUST 可通过配置调整，不得硬编码。

#### Scenario: 配额内的请求正常转发

- **WHEN** 单位时间内的请求数未超过配置的 QPS 配额
- **THEN** 所有请求正常转发到 `BootDemo`

#### Scenario: 超出配额立即拒绝

- **WHEN** 单位时间内的请求数超过配额
- **THEN** 超出的请求立刻收到 `429` 降级响应，网关不向 `BootDemo` 转发这些请求，调用方也不会被挂起等待

#### Scenario: 下一个周期配额恢复

- **WHEN** 上一个限流周期已过，新周期开始
- **THEN** 配额重置，请求恢复正常转发

#### Scenario: 限流不影响其他路径

- **WHEN** `/proxy/**` 已触发限流，同时客户端请求网关自身的 `GET /welcome`
- **THEN** `/welcome` 正常响应，不受 `/proxy` 配额影响

### Requirement: 统一的降级响应

被熔断或限流拦下的请求 SHALL 收到结构一致的 JSON 响应，而不是空响应体或网关内部异常堆栈。响应体 MUST 包含可区分拦截原因的标识、给人读的提示信息，以及本次请求的 traceId，便于调用方报障时定位。响应 MUST 使用 `application/json` 内容类型。

#### Scenario: 熔断降级响应

- **WHEN** 请求因熔断打开被拦下
- **THEN** 返回 `503`，响应体是 JSON，包含标识熔断原因的字段、提示信息和本次请求的 traceId

#### Scenario: 限流降级响应

- **WHEN** 请求因超出配额被拦下
- **THEN** 返回 `429`，响应体是 JSON，包含标识限流原因的字段、提示信息和本次请求的 traceId

#### Scenario: 降级响应携带的 traceId 与链路一致

- **WHEN** 客户端以 `X-Trace-Id: abc123...` 请求 `/proxy/welcome` 并被熔断或限流拦下
- **THEN** 响应体中的 traceId 与响应头 `X-Trace-Id` 一致，均为 `abc123...`

#### Scenario: 不泄漏内部细节

- **WHEN** 请求被熔断或限流拦下
- **THEN** 响应体中不包含异常堆栈、下游实例地址或框架内部类名

### Requirement: 未显式配置的实例走项目默认值

熔断、限流、超时三类保护 SHALL 各有一套项目级默认配置。任何没有单独配置的实例——无论是列了名字但未填参数，还是压根没有出现在配置里、由代码按名字临时创建——MUST 套用这套项目默认值，而不是 resilience4j 库自带的默认值。

库自带默认值对本网关是不安全的：限流的默认等待时长会阻塞事件循环，超时的默认值会把请求截断在一个过短的时限上。因此「漏配」MUST NOT 退化成「无保护」或「危险配置」。

单独配置的实例 MUST 继续以自己的取值为准，默认值只填补它没有覆盖的部分。

#### Scenario: 新路由引用未配置的实例名

- **WHEN** 新增一条路由，其熔断与限流过滤器引用的实例名没有出现在配置的实例列表中
- **THEN** 该路由仍受熔断与限流保护，参数取项目默认值，网关正常启动

#### Scenario: 未配置的限流实例不会阻塞

- **WHEN** 某个限流实例未被单独配置，其配额被耗尽
- **THEN** 超出配额的请求立即收到降级响应，调用方不会被挂起等待

#### Scenario: 未配置的超时实例不使用库默认值

- **WHEN** 某个熔断实例未被单独配置，下游响应耗时超过 1 秒但在项目默认超时以内
- **THEN** 请求正常返回，不被判定为超时

#### Scenario: 单独配置优先于默认值

- **WHEN** 某个实例单独配置了与默认值不同的配额或阈值
- **THEN** 该实例以自己的取值生效，默认值只填补它没有声明的项
