## ADDED Requirements

### Requirement: Netty 生产默认配置
系统 MUST 将设计中生产默认参数实际应用于客户端和服务端，包括固定默认且支持手动覆盖的线程数、有界执行器、监听 backlog、TCP_NODELAY、SO_KEEPALIVE、连接超时、池化分配器、写缓冲水位、连接及请求容量、报文预算与停机期限。系统 MUST 支持显式覆盖并校验范围及参数关系，不得静默忽略配置失败或依赖未声明的 Netty 默认值。

#### Scenario: 默认配置实际生效
- **WHEN** 调用方未覆盖参数并启动两端
- **THEN** 监听 backlog 为 1024，数据连接启用 TCP_NODELAY 和 SO_KEEPALIVE，写水位为 32 KiB/64 KiB，客户端连接超时为 1000 毫秒，服务端 boss/worker 线程数为 1/4，客户端 I/O 线程数为 2，业务线程数为 8，编解码及客户端完成线程数分别为 2，容量符合设计上限

#### Scenario: 线程数不随 CPU 核数变化
- **WHEN** 相同配置分别运行在不同可见 CPU 核数的机器，或调用方手动覆盖线程数
- **THEN** 默认线程数保持固定，覆盖后使用指定正整数；系统不调用按 CPU 计算线程数的逻辑，不省略 Netty 线程数或传入 0，非法线程数在启动前失败

#### Scenario: 覆盖与校验
- **WHEN** 调用方覆盖线程数、连接超时或水位
- **THEN** 合法配置在实际 Channel 和执行器生效；负数、溢出或低水位不小于高水位等非法组合在资源启动前失败

#### Scenario: 水位与字节硬上限
- **WHEN** 对端慢读或多个连接持续发送半包及大帧
- **THEN** 系统同时执行可写性检查、默认 16 MiB 单连接待写上限和 64 MiB 端级报文预算，超限拒绝或关闭，失败后释放预留字节，不将水位或逻辑字节预算宣称为进程总内存上限

### Requirement: 固定二进制帧与校验
系统 MUST 使用大端十九字节协议头，字段依次为四字节魔数、一字节版本、一字节消息类型、一字节序列化方式、八字节 requestId、四字节消息体长度，并使用 LengthFieldBasedFrameDecoder 拆帧。系统 MUST 拒绝非法头部、未知类型、未知序列化编号和超限消息。

#### Scenario: 粘包与半包
- **WHEN** 多个帧合并到一次读取，或一个帧在任意头部/消息体位置分段到达
- **THEN** 系统按顺序产出且仅产出完整消息，不丢失或重复消息

#### Scenario: 非法帧
- **WHEN** 收到旧协议、错误魔数、未知版本、超限长度或非法心跳体
- **THEN** 系统关闭连接且不调用业务，客户端终结该连接的在途请求

### Requirement: 统一同步异步与终态清理
客户端 MUST 提供 CompletableFuture 异步入口和委托同一机制的同步入口，以客户端共享等待表保存请求，发送前登记，并通过条件原子删除获得唯一终态所有权。系统 MUST 校验响应 Channel，处理取消、写失败、断连、关闭和迟到响应，回收计时与准入资源。

#### Scenario: 乱序响应
- **WHEN** 多个连接上的并发请求以不同顺序返回
- **THEN** 每个 Future 只收到属于自身 requestId 和 Channel 的结果

#### Scenario: 终态竞态
- **WHEN** 响应、取消、超时、写失败或关闭并发触发
- **THEN** 每个等待项只由一个终态路径取走，令牌和计时任务被回收，重复及迟到响应不改变结果

#### Scenario: 回调隔离
- **WHEN** 用户在 thenAccept 中执行阻塞操作
- **THEN** 用户回调不运行在 Netty I/O 或 HashedWheelTimer 线程，完成容量耗尽时新请求快速拒绝

### Requirement: 主动超时与截止时间
客户端 MUST 使用共享 HashedWheelTimer 主动管理请求超时，并为连接、写入及总调用设置上限；阶段预算不得超过剩余总预算。服务端 MUST 在业务开始前检查接收后剩余预算，不能将超时声明为副作用已撤销。

#### Scenario: 无等待者的异步请求
- **WHEN** 服务端不返回响应且调用方从未调用 get
- **THEN** 异步 Future 仍在截止时间到达后的调度窗口内失败，等待表归零

#### Scenario: 队列过期
- **WHEN** 请求在服务端业务队列中耗尽剩余预算
- **THEN** 服务端返回超时类别且不执行该业务方法

### Requirement: 发现与连接动态维护
系统 MUST 提供服务发现接口与 Nacos 注册、订阅、取消订阅和注销实现。系统 MUST 维护不可变候选快照，只路由到健康、已连接、可写且非排空实例；移除实例不得被迟到连接回调重新加入。

#### Scenario: 实例增减
- **WHEN** Nacos 推送上线、权重变化或下线快照
- **THEN** 候选列表动态更新，下线实例立即停止承接新请求且已有调用限时排空

#### Scenario: 注册中心故障
- **WHEN** 订阅不可用且最近成功快照超出配置有效期
- **THEN** 客户端拒绝新请求；有效空列表立即生效，不继续使用旧列表

#### Scenario: 局部断连
- **WHEN** 某实例连接断开
- **THEN** 只失败该连接的等待项，仍在线实例继续服务，断连实例按有界退避重连且不重复建立连接

### Requirement: 可插拔负载均衡
系统 MUST 提供 LoadBalancer 接口、轮询、平滑加权轮询及一致性哈希实现。策略 MUST 基于服务候选快照选择，不进行阻塞网络操作；一致性哈希要求明确路由键。

#### Scenario: 路由策略
- **WHEN** 固定候选集合接受连续请求
- **THEN** 轮询均匀轮转、加权策略按权重分配且过滤非正权重、相同哈希键稳定选择同一实例

#### Scenario: 无可用候选
- **WHEN** 服务没有满足健康及写入条件的 Channel
- **THEN** 调用快速返回无可用实例错误，不无限排队

### Requirement: 线程隔离与过载保护
服务端 MUST 将业务与较重序列化转换置于独立有界执行器；系统 MUST 设置客户端在途上限、服务端并发上限、有界业务队列、按服务速率限制及写缓冲上限。拒绝策略不得在 I/O 线程执行被拒绝业务。

#### Scenario: 业务池饱和
- **WHEN** 慢业务填满线程池和队列
- **THEN** 新业务得到过载错误，I/O 与心跳仍可推进，队列和等待表不突破配置上限

### Requirement: 心跳与优雅停机
系统 MUST 支持空闲心跳及失活连接关闭，并提供限时排空与幂等关闭。服务端 MUST 先停止新准入、注销实例并停止监听，再等待在途业务，最后释放连接与线程。客户端 MUST 停止新请求、发现订阅和重连，再限时排空并回收等待项及计时器。

#### Scenario: 对端失活
- **WHEN** 连接超过读空闲阈值无入站消息
- **THEN** 系统关闭连接并终结对应请求，心跳不进入业务调用表

#### Scenario: 排空期限
- **WHEN** 停机时存在一个可完成请求和一个持续阻塞请求
- **THEN** 期限内可完成请求正常结束，到期后剩余请求失败并关闭框架资源，重复关闭不报错

### Requirement: 有限安全重试
客户端 MUST 默认禁用重试，只有显式幂等调用能对连接或传输失败启用最多一次重试，所有尝试共享总预算并使用不同 requestId。超时、业务错误、过载及取消不得自动重试。

#### Scenario: 重试预算
- **WHEN** 幂等调用第一次发生传输失败且仍有预算
- **THEN** 客户端最多再尝试一次并优先排除失败实例，退避期间取消或预算耗尽则不发送

### Requirement: 安全与全链路观测
系统 MUST 保持服务签名白名单、限制报文与连接资源，支持可配置 TLS/mTLS 及证书校验。系统 MUST 记录低基数指标并通过 OpenTelemetry 传播追踪上下文，默认不记录参数、凭证或远端堆栈。

#### Scenario: 非法证书或方法
- **WHEN** 对端证书不可信、主机名不匹配或请求未注册方法
- **THEN** 握手或调用失败，业务不执行且不泄露内部堆栈

#### Scenario: 异步链路
- **WHEN** 一次调用跨客户端、网络、业务线程和响应完成线程
- **THEN** 追踪上下文保持关联，终态指标仅计一次，requestId 不作为指标标签

### Requirement: 可复现验证与迁移
实现 MUST 通过 JUnit 5 单元及环回集成测试，提供 Nacos 专项集成验证入口和压力验证说明。新旧协议 MUST 通过服务版本或端口隔离迁移，不能静默互通。

#### Scenario: 验证结果交付
- **WHEN** 实施完成并交付
- **THEN** 列出实际运行命令及结果，外部环境未运行的项目明确标记未验证，不宣称已达到未经测量的生产容量

### Requirement: JSON 与 Protostuff 双编码
系统 MUST 同时提供编号 1 的 JSON 和编号 2 的 Protostuff，实现客户端默认 JSON、客户端配置及单次调用覆盖。服务端 MUST 按每帧编号解码并以同一编码响应，客户端 MUST 校验响应编号；系统不得隐式切换编码。Protostuff 参数和结果 MUST 使用真实二进制序列化，不以 JSON 字符串作为中间传输模型。

#### Scenario: 同连接混合编码
- **WHEN** 同一连接并发发送 JSON 和 Protostuff 请求
- **THEN** 两类请求均正确还原参数与返回值，正常及业务错误响应分别保持请求编码，同步与异步行为一致

#### Scenario: 编码不匹配
- **WHEN** 请求使用未知或禁用编号，或响应与等待项预期编号不符
- **THEN** 系统关闭连接并失败对应在途调用，不降级或自动重试

### Requirement: 序列化类型与演进边界
系统 MUST 使用序列化器无关的带空值标记载荷及本地受控类型解码，区分 null、void、空字符串和空集合。Protostuff 协议字段 MUST 显式固定编号；系统 MUST 拒绝不支持类型和任意远端多态类加载，并限制解码嵌套深度及集合数量。

#### Scenario: 类型与字段兼容
- **WHEN** 两种编码分别传输基础值、受支持 DTO、明确泛型集合及日期时间，或新版 DTO 增加字段
- **THEN** 值按声明契约还原，旧接收方忽略未知字段，Protostuff 不重用已有编号，Java 21 环境测试通过

#### Scenario: 不安全或不受支持载荷
- **WHEN** 类型依赖未注册多态、未知 record 适配器，或载荷超过深度 64/集合元素 10000 的默认约束
- **THEN** 系统明确拒绝，解码期间执行资源限制，不加载网络指定类，也不悄悄改用 JSON
