# Design

## Context

对象列元数据在 `ExcelObjectMapper` 初始化时已按 `order`、再按继承层级和字段声明顺序排序并缓存。当前 `validateHeaders` 把标题转为 `Set`，仅检查标记为 `required` 的标题是否存在；后续映射再按标题名称查找字段，因此列顺序错误、额外列以及非必填声明列缺失都不会在标题阶段失败。标题回调发生在首条数据行之前，适合执行严格结构校验。

## Goals / Non-Goals

**Goals:**

- 复用已排序的列绑定，将其列表位置作为对象导入的期望零基列索引。
- 在数据行处理前一次性校验标题数量和每个位置的标题名称。
- 让异常包含足够的中文诊断信息，以便定位模板中的具体错误列。

**Non-Goals:**

- 不新增宽松/严格模式开关。
- 不改变 Map 导入的标题规则。
- 不改变 `order` 的数值含义或要求其从零、从一连续编号。
- 不改变 `required` 对数据单元格非空的约束。

## Decisions

### 1. 使用排序后列绑定的位置作为期望索引

`columns` 已由唯一的元数据扫描路径排序，导出也使用同一列表。标题校验直接逐索引比较 `headers.get(index)` 与 `columns.get(index).header()`，从而让导入模板与导出模板保持同一列契约。未显式设置 `order` 的字段继续按继承层级和声明顺序排列。

备选方案是把 `order` 数值直接解释为 Excel 列号，但现有声明普遍从 1 开始且允许不连续值，并且默认值为 `Integer.MAX_VALUE`，直接作为索引会破坏兼容性，因此不采用。

### 2. 先校验列数，再逐列校验标题

当标题数量不一致时立即抛出 `ExcelErrorType.MAPPING`，报告工作表、期望列数和实际列数；数量一致后再逐列比较，首次不一致时报告一基列号、期望标题和实际标题。这样避免缺列时的越界访问，也使错误原因单一明确。

备选方案是继续允许额外列或缺少非必填列，只校验已出现标题的位置；这会造成后续声明列整体移位，无法满足“列和声明一致”的严格模板契约，因此不采用。

### 3. 保留按标题名称的数据映射实现

本次只强化标题前置校验。校验通过后，现有按标题名称查找绑定的逻辑与索引结果等价，可减少实现范围并保留已有转换错误上下文。后续若需要优化，可在不改变外部契约的前提下独立改为直接按索引访问绑定。

## Risks / Trade-offs

- [现有乱序或带额外列的上传文件将不再兼容] → 在异常中明确给出期望与实际结构，调用方可使用对象导出的标题模板调整文件。
- [Java 反射字段声明顺序并非语言规范保证] → 显式配置 `order` 仍是生产模板稳定顺序的推荐方式；本次保持现有排序约定，不引入新的索引注解。
- [严格列数使非必填字段的标题也必须存在] → 明确区分“列结构必须存在”和“该列单元格值可以为空”，并通过测试固定该语义。

## Migration Plan

1. 上线前检查现有对象导入模板，确保标题数量和顺序与对应对象声明一致。
2. 对需要稳定长期兼容的字段显式配置唯一 `order`。
3. 若需回滚，恢复原有存在性校验及对应测试；该变更不涉及数据迁移或持久化格式变化。
