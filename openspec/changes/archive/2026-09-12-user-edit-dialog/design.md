## Context

当前用户列表已通过 `UserCreateDialog.vue` 完成弹窗新增；每行“编辑”按钮仍由 `UserListView.vue` 调用 Vue Router 跳转到 `/users/:id/edit`，再由 `UserFormView.vue` 加载用户详情并提交编辑。

本次只改变编辑用户的前端承载方式。现有 `getUser`、`updateUser` API、字段校验、结果提示和审批状态语义全部保持不变。

## Goals / Non-Goals

**Goals:**

- 在用户列表页内完成用户编辑，不离开当前列表。
- 编辑弹窗与新增弹窗保持一致的尺寸、字段布局、按钮层级和关闭行为。
- 打开弹窗后加载所选用户详情，避免展示上一次编辑对象的残留数据。
- 编辑成功后刷新列表，使已生效信息或待审批状态立即可见。
- 正确处理详情加载、校验失败、提交中、接口失败、关闭和切换编辑对象等状态。

**Non-Goals:**

- 不修改新增用户弹窗。
- 不允许编辑账号，不增加用户字段。
- 不修改后端接口、审批流程或待审批变更规则。
- 不重新设计用户列表，不引入状态管理库或新依赖。

## Decisions

### D1. 编辑弹窗作为独立组件

新增 `src/components/UserEditDialog.vue`，接收 `modelValue` 和待编辑的 `userId`，向父组件发出 `update:modelValue` 与 `updated` 事件。组件内部负责详情加载、表单状态、校验与更新请求。

编辑弹窗不与 `UserCreateDialog.vue` 合并为多模式组件。两者虽然字段相似，但数据加载、账号可编辑性、API 调用和成功事件不同；保持两个职责单一的组件可减少模式分支，并延续已确认的显式拆分策略。

### D2. 列表页维护当前编辑对象

`UserListView.vue` 新增 `editingUserId` 和编辑弹窗显示状态。点击某行“编辑”时，先保存该行用户 ID，再打开弹窗；收到 `updated` 事件后调用现有 `loadUsers()` 刷新列表。

列表页只管理选择和刷新，不复制编辑表单逻辑。

### D3. 详情加载与表单生命周期

- 弹窗打开时先清空表单与校验状态，再调用 `getUser(userId)` 获取最新详情。
- 详情加载期间对表单显示加载状态，并禁用提交按钮。
- 账号字段展示但保持只读；弹窗打开完成后聚焦姓名字段。
- 详情加载失败时关闭弹窗，错误信息继续由 `api/http.ts` 统一处理。
- 更新失败时不关闭弹窗，不覆盖用户已修改的数据。
- 弹窗关闭完成后重置表单、校验和加载状态，防止下次打开短暂显示旧数据。

### D4. 提交与关闭保护

提交前执行现有姓名必填与邮箱格式校验，校验通过后调用 `updateUser(userId, payload)`。提交期间按钮显示加载状态，并阻止重复提交、取消、Esc、遮罩和关闭按钮操作。

成功后根据 `result.effective` 显示“已生效”或“已提交审批”，关闭弹窗并发出 `updated` 事件。主要按钮文案使用“提交修改”，准确表达该操作可能直接生效，也可能进入审批。

### D5. 移除编辑页面路由

移除 `/users/:id/edit` 的 `user-edit` 路由，并删除不再被引用的 `UserFormView.vue`。编辑弹窗是列表内短暂操作，不创建 URL 查询参数或子路由。

## Visual Direction

沿用现有 `UserCreateDialog.vue` 和 Element Plus 的视觉体系：相同的响应式宽度、标签宽度、字段间距和底部操作区。新增与编辑通过明确的标题及主按钮文案区分，不增加装饰性元素。交互重点是从列表行原位进入编辑，完成后在同一列表位置看到更新结果。

## Risks / Trade-offs

- 移除 `/users/:id/edit` 后，旧编辑链接不再可用；当前产品已明确改用列表弹窗，本次接受这一变化。
- 打开弹窗需要一次详情请求，可能出现短暂加载；加载遮罩和禁用提交可避免用户编辑未完成初始化的数据。
- 新增与编辑弹窗存在少量表单结构重复，但各自流程清晰；当前字段数量不足以支持额外抽象的维护成本。
- 若用户关闭弹窗后立即编辑另一行，旧请求可能晚返回；实现时应确保只有当前打开对象的响应可以写入表单，避免异步结果串行污染。

## Open Questions

无。按照需求将编辑用户改为弹窗，其他用户管理行为保持不变。
