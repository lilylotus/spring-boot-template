# Change: 增加审批流程配置界面

## Why

项目后端已经具备审批总开关、按业务类型保存指定用户多级审批链的接口和存储，但前端没有配置入口。管理员目前无法在页面中选择审批人，也无法查看或修改是否启用审批流程，导致已经实现的用户新增/编辑审批能力无法完成日常配置。

## What Changes

- 在主导航新增“审批配置”，提供独立的 `/approval-settings` 页面。
- 页面展示全局审批开关；开启后，后续用户新增和用户编辑需要审批，关闭后直接生效。
- 分别为“用户新增”“用户编辑”维护顺序审批链，支持增加、删除和调整审批级别。
- 每个审批级别从系统用户中选择一个指定审批人，并显示姓名和账号，避免管理员直接填写难以识别的用户 ID。
- 保存前校验审批链至少一级、级别连续且审批人已选择；仅允许选择当前处于 `ACTIVE` 状态的用户作为新的审批人。
- 开启审批流程前要求用户新增和用户编辑两条审批链均已配置，前端给出明确提示，后端同时提供校验兜底。
- 配置变更只作用于之后发起的审批，已经运行中的审批继续使用发起时的审批人快照。

## Scope

### In Scope

- 复用现有 `approval_switch`、`approval_chain_config` 表及审批配置接口。
- 增强后端开启审批流程时的配置完整性校验。
- 新增前端审批配置类型、API 封装、页面、路由和导航入口。
- 为配置服务、Controller 和前端交互补充测试与构建验证。

### Out of Scope

- 按业务类型分别设置开关；本次仍使用现有全局总开关。
- 会签、或签、条件分支、审批角色或部门审批。
- 审批配置版本管理、历史配置回滚和配置变更审计。
- 修改或迁移已经运行中的流程实例。
- 新增登录鉴权和管理员权限模型。

## Impact

- **Frontend**：新增 `/approval-settings` 页面、审批配置 API 与类型，并修改顶部导航。
- **Backend**：复用现有查询/保存接口，增强 `PUT /api/approval/switch` 开启时的校验及对应测试。
- **Database**：不新增表，不修改现有表结构。
- **Compatibility**：现有用户管理、审批中心和进行中的审批实例保持兼容。

## Risks

- 已保存的审批人后续可能被停用或不存在。页面需要保留并标识旧配置，禁止在未重新选择有效用户的情况下保存；流程启动仍沿用现有审批链校验机制。
- 全局开关同时覆盖用户新增和用户编辑，因此只配置其中一条链时不能开启审批；页面需清晰展示缺失项。
