## Context

当前 `fronted/src/views/UserListView.vue` 中的“新增用户”按钮通过 Vue Router 跳转到命名路由 `user-new`；`fronted/src/views/UserFormView.vue` 同时承担新增与编辑两种模式。现有新增表单调用 `createUser`，根据 `UserOperationResultVO.effective` 显示“已生效”或“已提交审批”，随后返回列表页。

本次只改变新增用户的前端承载方式。用户管理仍使用 Vue3、TypeScript 与 Element Plus，接口与审批行为均不变。

## Goals / Non-Goals

**Goals:**

- 点击用户列表页“新增用户”后，在当前页面打开弹出窗口。
- 保留现有新增字段、校验规则、接口调用和结果提示语义。
- 成功提交后立即刷新列表，使新增用户及其状态可见。
- 正确处理打开、取消、提交中、失败重试和再次打开等弹窗状态。
- 保持键盘焦点、遮罩层、移动端宽度等 Element Plus 对话框的基础可用性。

**Non-Goals:**

- 不把编辑用户改为弹窗；编辑继续使用 `/users/:id/edit`。
- 不修改用户新增接口、审批开关或审批流程。
- 不重做用户列表的整体视觉设计，不新增全局状态管理或第三方依赖。
- 不改变账号唯一性等后端业务校验职责。

## Decisions

### D1. 新增弹窗作为独立组件

新增 `src/components/UserCreateDialog.vue`，由 `UserListView.vue` 控制其显示状态。弹窗组件拥有新增表单、校验、提交和重置逻辑，并在成功后向父组件发出 `created` 事件。

选择独立组件而不是把整段表单逻辑直接堆进列表页，是为了保持列表的数据加载职责与新增表单职责清晰；同时避免继续让 `UserFormView.vue` 通过路由状态兼任两个不同的交互容器。

### D2. 弹窗交互与状态

- 使用 Element Plus `el-dialog`，标题为“新增用户”，宽度在桌面端保持紧凑，在窄屏下使用视口宽度，避免横向溢出。
- 表单字段顺序沿用现有实现：账号、姓名、手机号、邮箱；账号和姓名必填，邮箱使用现有格式校验。
- 打开时聚焦第一个可输入字段；用户可通过关闭按钮、取消按钮、Esc 或点击遮罩关闭未提交的弹窗。
- 提交期间主按钮显示加载状态，并阻止重复提交和意外关闭。
- 接口失败时不关闭弹窗、不清空数据；统一错误消息继续由 `api/http.ts` 处理。
- 关闭完成后重置表单数据与校验状态，防止上一次输入或错误提示残留。

### D3. 成功后的列表同步

弹窗继续调用现有 `createUser(payload)`。成功后根据 `result.effective` 显示成功或信息提示，关闭弹窗并发出 `created` 事件；`UserListView.vue` 收到事件后调用现有 `loadUsers()` 刷新列表。

列表刷新失败时仍由统一响应拦截器提示，弹窗不重新打开，避免重复创建用户。

### D4. 路由与编辑表单收敛

移除 `/users/new` 的 `user-new` 路由。`UserFormView.vue` 收敛为编辑用户页面，只处理 `/users/:id/edit`，保留详情加载、编辑提交和返回列表的行为。

不为弹窗状态创建 URL 查询参数或子路由。本次新增是用户列表内的短暂操作，不需要刷新恢复或可分享链接；保持局部状态能减少路由与弹窗状态同步的复杂度。

## Visual Direction

沿用当前管理后台与 Element Plus 的配色、字体和组件密度，不引入新的视觉体系。弹窗以清晰的字段层级和稳定的底部操作区为重点：次要“取消”与主要“创建用户”动作保持明确区分。唯一的交互强调是提交完成后列表在原位刷新，让用户能立即看到新记录及其审批状态。

## Risks / Trade-offs

- 移除 `/users/new` 后，旧书签不能继续打开独立新增页；该前端尚处早期阶段，且新增动作已明确改为列表内弹窗，本次接受这一变化。
- 新增与编辑表单不再共用同一个页面组件，存在少量字段与规则重复；当前字段很少，显式拆分比引入过度抽象更容易维护。后续若字段明显增加，再抽取纯表单字段组件。
- 提交成功后的列表刷新会产生一次额外查询，但能确保列表状态以后端最终结果为准，符合现有前后端职责边界。

## Open Questions

无。按照需求仅将“新增用户”改为弹出窗口，编辑用户保持原交互。
