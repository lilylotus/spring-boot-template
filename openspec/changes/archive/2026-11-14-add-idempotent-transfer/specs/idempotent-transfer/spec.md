# Spec Delta

## Purpose

提供一个以调用方幂等键保证"同一笔转账请求无论到达多少次都只执行一次"的转账接口，
作为模板中资金类写接口实现接口幂等的参考行为约定。

## ADDED Requirements

### Requirement: 提交转账请求
系统 SHALL 提供 `POST /api/transfers` 接口，接收请求头 `Idempotency-Key` 以及 JSON 请求体
（转出账户号、转入账户号、金额、可选备注），转账成功时以统一响应结构返回该笔转账的流水号、
幂等键、转出账户号、转入账户号、金额、状态和创建时间。

#### Scenario: 转账成功
- **WHEN** 调用方携带一个从未使用过的 `Idempotency-Key`，提交从余额充足的账户 A 向账户 B 转账 100.00 的请求
- **THEN** 系统返回 HTTP 200 的统一成功响应，其中包含流水号且状态为成功
- **AND** 账户 A 的余额减少 100.00，账户 B 的余额增加 100.00

### Requirement: 转账请求参数校验
系统 MUST 在执行任何资金变动之前校验请求：`Idempotency-Key` 必填且长度不超过 64 个字符；
转出账户号、转入账户号必填；金额必填、大于 0 且最多两位小数；转出账户与转入账户不得相同。
校验不通过时系统 MUST 返回 HTTP 400 的统一错误响应，且不产生转账流水、不改变任何账户余额。

#### Scenario: 缺少幂等键
- **WHEN** 调用方提交的转账请求没有携带 `Idempotency-Key` 请求头
- **THEN** 系统返回 HTTP 400 的统一错误响应，且任何账户余额都不发生变化

#### Scenario: 金额不合法
- **WHEN** 调用方提交金额为 0、负数或超过两位小数的转账请求
- **THEN** 系统返回 HTTP 400 的统一错误响应，且任何账户余额都不发生变化

#### Scenario: 转出与转入为同一账户
- **WHEN** 调用方提交转出账户号与转入账户号相同的转账请求
- **THEN** 系统返回 HTTP 400 的统一错误响应，且该账户余额不发生变化

### Requirement: 转账业务规则
系统 MUST 保证一笔转账的扣款与入账要么同时生效、要么同时不生效，且任何账户余额都不会被扣成负数。
转出或转入账户不存在时系统 MUST 返回 HTTP 404；转出账户余额不足时系统 MUST 返回 HTTP 422。
业务规则不满足时不产生转账流水、不改变任何账户余额。

#### Scenario: 账户不存在
- **WHEN** 调用方提交的转出账户号或转入账户号在系统中不存在
- **THEN** 系统返回 HTTP 404 的统一错误响应，且任何账户余额都不发生变化

#### Scenario: 余额不足
- **WHEN** 调用方提交的转账金额大于转出账户当前余额
- **THEN** 系统返回 HTTP 422 的统一错误响应，且转出、转入账户余额都不发生变化

#### Scenario: 并发转账不透支
- **WHEN** 多个使用不同幂等键的转账请求同时从同一账户转出，且金额合计超过该账户余额
- **THEN** 只有余额足以覆盖的那部分请求成功，其余请求返回 HTTP 422
- **AND** 该账户最终余额不为负数

### Requirement: 重复请求幂等
对于已经成功执行过的 `Idempotency-Key`，系统 MUST NOT 再次执行资金划转；当重复请求的内容
（转出账户号、转入账户号、金额）与首次请求一致时，系统 SHALL 返回 HTTP 200 以及与首次执行
相同的转账结果（相同的流水号、金额、状态和创建时间）。

#### Scenario: 成功后重试
- **WHEN** 一笔转账已成功，调用方使用相同的 `Idempotency-Key` 和相同的请求内容再次提交
- **THEN** 系统返回 HTTP 200，响应中的流水号与首次响应相同
- **AND** 转出、转入账户余额与首次转账完成后保持一致，没有被再次扣减或增加

#### Scenario: 并发重复提交
- **WHEN** 多个携带相同 `Idempotency-Key` 和相同请求内容的转账请求同时到达
- **THEN** 至少一个请求返回 HTTP 200，所有返回 HTTP 200 的响应流水号相同，其余请求返回 HTTP 409
- **AND** 转出账户只被扣款一次，转入账户只入账一次，系统中只存在一条对应的转账流水

### Requirement: 处理中的重复请求立即拒绝
当某个 `Idempotency-Key` 的转账请求正在处理、尚未得出结果时，系统 MUST 立即以 HTTP 409 的统一
错误响应拒绝携带相同 `Idempotency-Key` 的其他请求，提示请求正在处理中；被拒绝的请求不等待、
不执行转账、不改变任何账户余额。不同 `Idempotency-Key` 的请求互不影响。

#### Scenario: 首个请求处理期间重复提交
- **WHEN** 一个转账请求正在处理中，另一个携带相同 `Idempotency-Key` 的请求到达
- **THEN** 后到的请求立即收到 HTTP 409 的统一错误响应，提示请求正在处理中
- **AND** 后到的请求不产生转账流水、不改变任何账户余额

#### Scenario: 被拒绝后稍后重试
- **WHEN** 一个请求因相同 `Idempotency-Key` 的请求正在处理而收到 HTTP 409，待首个请求成功完成后使用相同的 `Idempotency-Key` 和请求内容再次提交
- **THEN** 系统返回 HTTP 200，响应中的流水号与首个请求的响应相同，账户余额没有被再次变动

#### Scenario: 不同幂等键互不阻塞
- **WHEN** 一个转账请求正在处理中，另一个携带不同 `Idempotency-Key` 的转账请求到达
- **THEN** 后到的请求不会因前者正在处理而被拒绝

### Requirement: 幂等防护不可被绕过
系统 MUST NOT 在并发防护机制不可用时放行转账：无法确认某个 `Idempotency-Key` 是否正在被处理时，
系统 MUST 返回 HTTP 500 的统一错误响应且不执行转账。无论并发防护是否提前失效，系统 MUST 保证
同一 `Idempotency-Key` 最多产生一条转账流水、最多发生一次资金划转。

#### Scenario: 并发防护依赖的存储不可用
- **WHEN** 并发防护所依赖的存储发生故障，调用方提交转账请求
- **THEN** 系统返回 HTTP 500 的统一错误响应，且任何账户余额都不发生变化

#### Scenario: 并发防护提前失效
- **WHEN** 两个携带相同 `Idempotency-Key` 的请求因并发防护提前失效而同时进入转账执行
- **THEN** 只有一个请求完成资金划转并产生转账流水，另一个请求不改变任何账户余额

### Requirement: 幂等键与请求内容不一致时拒绝
当 `Idempotency-Key` 已被一笔成功的转账使用，而新请求的转出账户号、转入账户号或金额与那笔转账
不一致时，系统 MUST 返回 HTTP 409 的统一错误响应，且不执行转账、不改变任何账户余额。
该响应的提示信息 MUST 与"请求正在处理中"的提示信息不同，使调用方能够区分二者。

#### Scenario: 同一幂等键提交不同金额
- **WHEN** 一笔 100.00 的转账已成功，调用方使用相同的 `Idempotency-Key` 提交金额为 200.00 的转账请求
- **THEN** 系统返回 HTTP 409 的统一错误响应
- **AND** 任何账户余额都不发生变化，原转账流水保持不变

### Requirement: 失败请求不占用幂等键
因参数校验或业务规则不满足而失败的转账请求 MUST NOT 占用其 `Idempotency-Key`：
调用方排除失败原因后使用同一幂等键重新提交时，系统 SHALL 把它当作一笔新的转账正常执行。

#### Scenario: 余额不足后充值重试
- **WHEN** 一笔转账因余额不足返回 HTTP 422，之后转出账户余额变为充足，调用方使用相同的 `Idempotency-Key` 再次提交相同请求
- **THEN** 系统执行转账并返回 HTTP 200 的统一成功响应
