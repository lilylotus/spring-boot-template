## 背景

当前 `RpcClient` 使用 UUID 字符串、单 Channel、Netty Promise 和阻塞等待超时；服务端已有有界业务池，但关闭时直接 `shutdownNow()`。本次沿用服务接口白名单，将参数与结果改为序列化器无关的载荷，重构协议、客户端生命周期及集群路由。所有自然语言使用中文，实施前需用户审阅本变更。

## 目标与非目标

目标是支持多实例生产设计：协议边界明确、资源有界、请求至多完成一次、同步异步同源、故障可隔离、生命周期可验证。

不实现流式调用、跨语言 SDK、动态代理生成、透明恰好一次语义、ZooKeeper 适配器或监控平台部署。同时提供 JSON 和 Protostuff 序列化实现；生产容量需部署环境压测后确认。

## 技术决策

### 0. Netty 生产默认参数

默认值是本框架为内部网络、长连接、普通请求响应业务选择的保守起点，不是 Netty 官方推荐值或对所有硬件的容量承诺。默认配置必须直接应用到实际 Bootstrap 和执行器，不仅写在示例中。所有框架自建线程组和执行器使用固定默认线程数，允许部署手动覆盖；禁止根据 `availableProcessors()` 推导线程数量，禁止使用省略线程数或传入 `0` 的 Netty 自动配置入口。Netty 线程数通过 `serverBossThreads`、`serverWorkerThreads`、`clientIoThreads` 配置，必须为正整数，并显式传入线程组构造器；不写入机器专属 JVM 路径或修改进程级 Netty 系统属性。

| 配置项 | 默认值 | 应用位置与意图 |
| --- | --- | --- |
| 传输实现 | NIO | 沿用 Netty 4.2 `MultiThreadIoEventLoopGroup` 与 `NioIoHandler`，兼容当前 Windows 及 Linux；原生传输后续按实测扩展 |
| 接收连接线程 | `1` | 服务端 boss，共享于该服务端监听器 |
| 服务端 I/O 线程 | `4` | worker，不承担业务和重型序列化转换 |
| 客户端 I/O 线程 | `2` | 每客户端所有实例连接共享，禁止每连接创建线程组 |
| 业务线程数 | `8` | 固定核心/最大线程数，有界队列 `256`，`AbortPolicy` |
| 编解码工作线程 | `2` | 每端独立固定池，队列 `256`；解码前即执行报文字节准入 |
| 客户端完成线程 | `2` | 固定池，队列 `1024`，按请求预留完成容量 |
| `SO_BACKLOG` | `1024` | 服务端 `.option`；实际积压受操作系统上限约束，不等于已接受连接数 |
| `SO_REUSEADDR` | `true` | 服务端监听 `.option`；不启用 `SO_REUSEPORT`，不用于多进程共享监听 |
| `TCP_NODELAY` | `true` | 服务端 `.childOption` 和客户端 `.option`，适用于低延迟小报文 |
| `SO_KEEPALIVE` | `true` | 两端数据连接；系统保活只作补充，故障检测由应用心跳负责 |
| `CONNECT_TIMEOUT_MILLIS` | `1000` | 客户端建连；调用阶段仍受剩余总预算约束 |
| `ALLOCATOR` | `PooledByteBufAllocator.DEFAULT` | 两端数据连接显式设置、共享分配器，避免依赖 Netty 版本隐式默认值 |
| `WRITE_BUFFER_WATER_MARK` | 低位 `32 KiB`，高位 `64 KiB` | 两端数据连接；使用统一选项，不使用已弃用的高低水位单独选项 |
| `AUTO_READ` | `true` | 默认保持心跳和响应读取，入站资源不足时拒绝或关闭，不无限滞留消息 |
| `ALLOW_HALF_CLOSURE` | `false` | RPC 不支持半关闭会话 |
| `SO_SNDBUF`、`SO_RCVBUF` | 不显式设置 | 保留操作系统自适应；如覆盖必须为正并记录实际生效值 |
| `SO_LINGER` | 不显式设置 | 不通过阻塞式 linger 实现停机，使用框架排空 |
| 最大消息体 | `8 MiB` | 帧上限为 `8 MiB + 19`，请求响应两端一致 |
| 每 Channel 待写字节硬上限 | `16 MiB` | 框架在提交写入前按实际编码长度原子预留，写完成后释放 |
| 每端报文缓冲预算 | `64 MiB` | 每客户端/服务端实例分别统计入站累积、等待解码及待写报文字节，超过预算拒绝或关闭连接 |
| 客户端最大在途请求 | `1024`，每连接 `128` | 包含连接等待阶段；完成槽独立预留，用户回调未释放槽时不接受替代请求 |
| 服务端最大连接数 | `1024` | 接受后立即原子准入，超限关闭；与 backlog 分开控制 |
| 客户端最大连接数 | `128` | 全客户端上限，默认每实例一个 Channel；超限实例暂不连接并记录指标 |
| 服务端最大在途请求 | `业务线程数 + 256`，每连接 `128` | 包括排队和执行；任一资源阈值耗尽立即拒绝 |
| 每服务速率与突发容量 | `1000 次/秒`，`200 次` | 本服务端实例内令牌桶，可按服务覆盖，不宣称集群全局限流 |
| 心跳写空闲 / 读失活 | `15 秒 / 45 秒` | 每连接至多一个未完成心跳，控制消息也计入内存预算 |
| 总调用 / 单次写入超时 | `5 秒 / 1 秒` | 独立请求预算；写超时视连接异常并关闭，不能代替响应超时 |
| TLS 握手超时 | `3 秒` | 只在启用 TLS 时应用，调用方总截止时间可更早结束等待 |
| 计时轮 | 刻度 `10 毫秒`、槽数 `512` | 每客户端共享一个计时器，待处理请求数量由准入控制 |
| 重连退避 | 初始 `200 毫秒`、上限 `10 秒`、上下 `20%` 抖动 | 每实例最多一个重连任务，与调用重试分开 |
| 业务排空 / 资源关闭 | `30 秒 / 5 秒` | 排空后所有资源共享一次 5 秒关闭预算，不能逐连接累加 |
| EventLoop 停机静默期 | `0` | 完成准入关闭和排空后调用 `shutdownGracefully`，timeout 使用剩余资源关闭预算 |

水位只改变 `Channel.isWritable()`，不阻止继续写入，也不是内存硬上限。客户端在不可写时不再选用该连接；服务端不积累额外无界响应队列，响应经字节预算准入后提交，无法准入时关闭慢消费者连接并清理其调用。单帧允许大于高水位，但必须满足帧上限、单连接硬上限和端级报文预算。字节预留、编码失败、写失败、取消、断连的释放路径必须成对验证。

入站累积也要统计字节预算，不能等完整帧进入业务池后才计费，否则大量半包连接仍可耗尽内存。`64 MiB` 是框架持有的逻辑报文预算，不是进程总内存或池化分配器的保留内存上限；JVM 堆、直接内存、线程栈、反序列化对象和 Nacos SDK 需另做部署预算。实现必须暴露池化内存和报文占用指标，并以慢发包及最大帧并发测试验证内存变化。

泄漏检测保持进程已有配置，不在 RPC 库中调用全局 setter；部署文档使用 `SIMPLE` 作为生产基线，专项验证启用 `PARANOID`。日志记录脱敏后的实际框架配置、CPU 数和传输类型。所有数量、时长和字节上限校验范围与溢出；校验低水位小于高水位、单帧不超过硬上限、端级预算至少容纳一帧、完成容量能够覆盖已准入请求。启动或建连选项设置失败不得静默忽略。

参数 API 与水位语义依据 [Netty ChannelOption](https://netty.io/4.2/api/io/netty/channel/ChannelOption.html)、[WriteBufferWaterMark](https://netty.io/4.2/api/io/netty/channel/WriteBufferWaterMark.html) 及 [PooledByteBufAllocator](https://netty.io/4.2/api/io/netty/buffer/PooledByteBufAllocator.html)；上述具体容量和固定线程默认值为本项目设计选择，实施时以已锁定版本验证。

### 1. 固定头协议

全部多字节字段使用大端序，长度只计消息体，默认最大消息体 8 MiB。

| 字段 | 偏移 | 字节数 | 约定 |
| --- | --- | --- | --- |
| 魔数 | 0 | 4 | `0x52504331` |
| 版本 | 4 | 1 | `1` |
| 消息类型 | 5 | 1 | `1` 请求、`2` 响应、`3` 心跳请求、`4` 心跳响应 |
| 序列化方式 | 6 | 1 | `1` JSON、`2` Protostuff，心跳为 `0` |
| requestId | 7 | 8 | 正数；心跳使用独立关联标识 |
| 消息长度 | 15 | 4 | 非负消息体字节数 |
| 消息体 | 19 | 可变 | 按序列化编号编码的请求/响应；心跳为空 |

使用 `LengthFieldBasedFrameDecoder(maxBodyLength + 19, 15, 4, 0, 0, true)` 保留头部，配置时检查整数溢出。帧解析后校验魔数、版本、类型、序列化编号及长度；未知或非法帧关闭连接，触发对应在途请求失败。请求响应 requestId 以头部为唯一来源，消息体不重复存储。响应错误放在响应体，参数与结果使用带空值标记的字节载荷，替代旧 JsonNode 参数及 JSON 字符串结果约定。

JSON/Protostuff 解码、参数转换和编码可能消耗 CPU：EventLoop 只做帧边界与轻量头检查、投递；大消息序列化转换在有界工作执行器执行，编码结果回到 Channel 写出。禁止 Java 原生反序列化及远端任意类型加载。长度解码器无需自行维护 TCP 拆包状态机。[Netty 官方参数说明](https://netty.io/4.2/api/io/netty/handler/codec/LengthFieldBasedFrameDecoder.html)

### 1.1. JSON 与 Protostuff 双序列化

`MessageSerializer` 统一提供编号、按明确目标类型编码/解码的接口；注册表启动时固定，禁止重复编号。客户端默认 `JSON`，支持客户端级配置和单次调用覆盖；服务端默认同时启用 `JSON` 与 `PROTOSTUFF`。每帧独立选择序列化器，同一连接允许混合请求。成功及业务错误响应均沿用请求编号，客户端 PendingRequest 保存预期编号并校验响应；编号不匹配按协议错误处理，不隐式降级或重试。未知或禁用编号关闭连接，不能假设对端理解另一种错误编码。

请求信封包含服务名、方法签名、超时预算、追踪信息及参数载荷列表；每个载荷由显式 `isNull` 和 `byte[] data` 组成，响应结果使用相同载荷结构。信封与非空参数/返回值都使用头部所选格式编码。JSON 信封中的字节数组按 Base64 表示，Protostuff 信封直接保存二进制；Protostuff 路径不得先转换成 JSON 字符串或 JsonNode。该统一结构牺牲 JSON 的直接可读性以避免传输层依赖 Jackson，Base64 扩张及内外两次编码都计入大小与内存预算。失败、void、空字符串、空集合和 null 必须有明确不同语义。

服务端先解码固定信封并匹配本地注册的方法签名，再根据本地参数类型解码参数；客户端按明确返回类型解码结果。扩展基于 `Type` 的入口支持具体泛型集合，原 `Class<T>` 入口保留并委托；不将网络类名交给 Class.forName，也不使用任意 Object 多态恢复。JSON 继续使用 Jackson 3，保留未知字段兼容和现有日期时间文本规则。

Protostuff 使用 `protostuff-core`、`protostuff-runtime`，实施时锁定一致版本并验证 Java 21。协议 DTO 使用内置字段名称到编号的固定映射 Schema，业务 DTO 使用全字段 `@Tag`，不依赖字段声明顺序；字段编号只增不复用。对允许的具体业务 DTO 缓存 Schema 字段布局，基础值、数组和具有明确元素类型的集合通过受控包装 Schema 处理；null 由外层标记处理。限制类型嵌套深度及集合元素数，默认分别为 64 和 10000，并在解码分配过程中执行约束，不仅在对象创建后检查。日期时间使用显式标量适配器，不能依赖对 JDK 内部字段的反射；record 或不可变类型需要显式 Schema/适配器，注册时验证，不承诺 RuntimeSchema 自动支持所有 Java 类型。

Schema 仅为本地注册契约生成；拒绝缺失元素类型的集合、未注册的 Object/接口多态及循环对象图，禁止自动按远端元数据加载多态类。每次调用独立使用并 finally 清理 LinkedBuffer，Schema 缓存随框架实例释放，不并发共享可变编码缓冲。对于不受支持的类型在注册或调用发送前明确失败，不默默切换 JSON。

使用 [Protostuff Schema](https://protostuff.github.io/documentation/schema/) 和 [Runtime Schema](https://protostuff.github.io/docs/protostuff-runtime/) 的字段编号与静态类型机制；实际受支持类型列表、字段演进规则和 Java 21 验证结果随实现交付。协议仍为尚未发布的版本 1，旧格式继续按既定隔离迁移策略处理。

### 2. 请求生命周期与异步完成

`invokeAsync` 返回 `CompletableFuture<T>`；原 `invoke` 委托相同内部调用并等待结果，同步调用禁止在 I/O、计时器与框架完成线程执行。客户端级共享表覆盖该客户端全部连接，而非静态 JVM 全局表，避免多个客户端互相清理。

`PendingRequest` 保存原始 Future、所属 Channel、单调时钟截止时间、超时句柄、容量令牌和追踪上下文。客户端 `AtomicLong` 生成正数 requestId，耗尽后拒绝新调用而非回绕复用；重连不重置计数。先预留准入资源，再登记等待项与计时任务，最后发送。关闭与登记通过生命周期门控防止漏项。

响应、超时、写失败、取消、断连和关闭统一以 `remove(id, pending)` 竞争终态所有权；响应必须校验来源 Channel。获胜者取消计时、释放令牌、记录一次结果，并将完成通知投递到独立有界完成池。完成池容量纳入准入预留，释放完成槽前不得接收替代请求，关闭时排空；不允许拒绝后在 EventLoop 或计时器线程执行用户回调。返回 Future 的取消传播至底层等待项。定时句柄安装与提前终态竞争时，安装方必须立即取消已无等待项的句柄。

调用方无需 `.get()` 也会超时。采用每客户端一个共享 `HashedWheelTimer`，不为每请求创建计时器。计时器仅做终态竞争和投递；完成 Future 可能同步执行用户 `thenAccept`，因此绝不直接在计时线程或 I/O 线程调用 complete。用户长时间阻塞回调仍会耗尽完成池，届时新请求快速拒绝，并在文档推荐耗时回调使用自有执行器。

### 3. 分级超时与重试

总调用预算默认 5 秒，连接默认 1 秒、写入默认 1 秒，可按调用覆盖；每阶段取配置和剩余总预算的较小值。总预算覆盖连接等待、排队、发送、响应和框架结果转换，使用 `System.nanoTime()` 计算本地剩余时间。计时轮默认 10 毫秒刻度，超时调度存在刻度和线程调度误差，不承诺硬实时。

请求体携带发送时剩余预算 `timeoutMillis`。服务端从接收时刻建立本地截止时间，业务队列出队前再次检查；网络传输时间由客户端总截止时间兜底，不假定两端时钟同步。已执行任务超时后仅尽力中断，不承诺回滚副作用。

默认不重试。只有显式幂等调用可配置最多一次重试，候选限于连接失败或传输失败，采用有抖动退避、独立 attempt requestId、共享逻辑调用截止时间，并优先排除失败实例。响应超时、远端业务错误、限流和取消均不自动重试。写失败可能已到达服务端，幂等键与持久化去重仍由业务承担；取消与截止时间阻止尚未发送的重试。

### 4. 动态发现、连接与负载均衡

`ServiceDiscovery` 提供订阅、取消订阅、实例快照；注册职责单独抽象，避免与当前本地 `ServiceRegistry` 混淆。首期 Nacos 负责实例注册/注销及订阅，配置 namespace、group、服务版本、地址、凭证和权重，秘密来自外部配置。服务端绑定成功且具备处理能力后才注册；注册失败回滚启动。[Nacos 官方 Java SDK](https://nacos.io/docs/v2.4/manual/user/java-sdk/usage/)

注册中心回调只发布不可变快照到串行发现执行器。每服务按稳定实例标识维护连接，新增实例异步连接，连接成功后进入可选列表。移除实例立即停止新分配，已有请求限时排空后关闭。用本地代次防止迟到连接成功回调复活已移除实例；SDK 事件若无版本，不虚构其全局排序保证。

连接断开只失败该连接请求。对仍在发现快照的实例按有上限指数退避和抖动重连，每实例最多一个连接建立任务。发现不可用时仅在可配置缓存有效期内使用已有健康连接（默认 30 秒），过期后拒绝新调用；启动无快照直接失败。有效空列表立即摘除全部实例，不误当成订阅异常。

`LoadBalancer` 在对应服务的当前 active、健康、非排空、可写 Channel 及实例元数据快照上选择，不执行网络操作。默认轮询；平滑加权轮询过滤非正权重，一致性哈希使用稳定实例标识和虚拟节点，要求调用显式提供路由键。无候选快速失败；选择后状态变化按发送失败处理，不能在锁内连接或等待。

### 5. 服务端容量与安全边界

继续使用独立有界业务池及 `AbortPolicy`，禁止 `CallerRunsPolicy`。增加客户端最大在途数、服务端全局和单连接并发上限、按服务令牌桶速率限制以及 Channel 写缓冲水位。准入失败返回稳定过载类别；不可写时限制排队，不能无限缓存响应。心跳走独立轻量控制路径，不占业务队列。

只调用已注册服务接口签名。支持配置 `SslContext`，生产跨可信网络边界部署要求 TLS 与主机名校验，可选 mTLS；禁止信任所有证书。TLS 握手限时、连接数量与帧大小有界；失败返回安全错误，完整堆栈仅本地日志，禁止默认打印参数和凭证。

### 6. 心跳与停机

`IdleStateHandler` 默认写空闲 15 秒发心跳，读空闲 45 秒视为失活；参数可配置且读阈值大于心跳间隔。心跳响应验证关联标识，独立于业务 pending 表且同样有界。正常流量刷新活性。

生命周期为 `NEW → RUNNING → DRAINING → CLOSED`。服务端先进入排空、注销发现并停止监听；已有连接拒绝新请求，允许在途响应完成，默认最多等待 30 秒，随后关闭子 Channel、执行器和 EventLoop。注销失败仍执行本地排空并记录错误，避免无限阻塞停机。

客户端停止准入和重连、取消订阅、限时等待已有调用；期限到则终结剩余请求，然后停止计时器、连接、完成池和 EventLoop。`closeAsync` 不阻塞框架线程；同步 `close` 在框架线程拒绝调用，外部线程等待。重复关闭幂等，部分启动失败也释放已取得资源。

### 7. 可观测性与验证

Micrometer 记录调用量、错误类别、调用/阶段延迟、在途数、业务队列深度、拒绝数、连接数、发现变更、重连和心跳超时。标签只使用受控服务名、方法名及结果类别，requestId/实例动态地址不作为高基数标签。OpenTelemetry 注入/提取 W3C 追踪上下文，在客户端尝试和服务端执行处建立 span，异步切换显式恢复上下文；采集异常不影响调用。

单元测试采用 EmbeddedChannel、可注入时钟/调度器和线程屏障覆盖拆包与竞态。环回测试覆盖多节点、断连、半关闭、过载、心跳与停机；Nacos 专项集成测试使用显式外部测试配置，不将缺失环境报成测试成功。压力验证记录环境、吞吐、p95/p99、错误率和资源曲线，证明有界负载下拒绝行为和停止后的资源回收，不虚构通用吞吐保证。

## 风险与取舍

- 协议不兼容 → 新旧服务使用不同端口及服务版本，整组切换和回滚。
- 序列化转换与多执行器增加调度成本 → 保持池与队列有界，基于测量调节，不将序列化直接放回 I/O 线程。
- 超时不等于远端停止 → 文档明确副作用边界，重试默认关闭。
- 注册中心缓存可能短期路由陈旧实例 → 有效期、健康检测和本地连接校验共同约束。
- 新依赖可能带来 Netty/Jackson 冲突 → 实施先检查依赖树及实际运行，不盲目强制覆盖 SDK 依赖。

## 迁移计划

用户确认后按协议、异步生命周期、发现路由、生产治理顺序实施并逐项测试。保留旧调用参数入口，明确 requestId 模型破坏性变更。上线使用独立服务版本完成客户端与服务端配套切换；失败时整组退回旧版本。归档前核对旧变更规范冲突，不能同时宣称旧 Promise 与新 CompletableFuture 均是当前契约。

## 待确认事项

方案默认采用 Nacos、三种负载均衡策略、可选 TLS/mTLS 和实际监控接入。部署规模及延迟指标尚未给定，以配置和可复现压测结果作为容量验收依据；这不阻碍方案审阅。

## 实施细化

Protostuff 使用手写的受控类型 Schema：空值字段编号为 1、标量为 2、集合元素为 3、映射值为 4、非空容器标记为 5；DTO 字段编号为声明标签加 10。协议 record 使用固定字段名称映射，不依赖声明顺序；业务 DTO 首期为带无参构造和显式 @Tag 的普通类，不支持继承字段、任意业务 record 或不可变类。JSON 仍支持本地明确声明的 record。JSON 在对象构造前流式检查嵌套及集合限制。发现健康检查和重试调度线程各为固定 1 个，不根据 CPU 推导；第三方 Nacos SDK 自身线程配置由其部署配置管理。

停机期限约束框架等待时长；Java 无法强制终止不响应中断的业务或用户回调。完成池在截止后保持关闭准入并继续排空已排队的终态通知，不能使用 shutdownNow 丢弃这些通知；用户回调永久阻塞会延迟通知与对应守护线程回收。独立重试完成池同样使用固定 2 个线程和有界预留容量，防止重试总超时在线程调度器执行用户回调。
