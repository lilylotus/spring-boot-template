## Context

`ApprovalTask` 与 `ApprovalRecord` 仅提供 `bizType`、`bizId`，其中用户新增/编辑业务的 `bizId` 是用户 ID。`ApprovalCenterView.vue` 已加载完整用户列表并传给详情弹窗，可复用该数据完成展示映射。

## Goals / Non-Goals

**Goals:** 在待审批和审批记录列表中直观显示被审批用户姓名，同时保留异常数据的可识别性。

**Non-Goals:** 不改变 `bizId` 的接口含义、审批动作请求参数、数据库关联关系和审批详情展示。

## Decisions

### D1. 前端展示层映射，不扩展后端 DTO

在 `ApprovalCenterView.vue` 增加统一的显示函数：当 `bizType` 为 `USER_CREATE` 或 `USER_EDIT` 时，用字符串形式的用户 ID 匹配 `users` 中的记录并返回 `realName`。两个列表共用该函数，列标题统一改为“审批用户”。现有用户列表请求足以支持映射，无需让审批模块依赖身份模块的数据访问层，也无需增加网络请求。

### D2. 无法映射时回退原业务 ID

若用户列表尚未加载、请求失败、目标用户不存在、姓名为空或业务类型未知，显示原 `bizId`。该策略避免加载时短暂空白，并允许历史、迁移或未来业务类型继续定位原始单据。

## Risks / Trade-offs

- 用户列表与审批数据并行加载时，页面可能先短暂显示 ID，用户列表返回后 Vue 响应式渲染会自动替换为姓名。
- 当前方案适合已有数据规模；若用户列表未来改为分页，应由后端提供独立业务展示名称字段。
