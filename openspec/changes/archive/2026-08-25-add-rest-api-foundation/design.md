## Context

参见 `proposal.md` 的变更动机。项目已经引入 Spring Web 与 Jakarta Validation，并由 `TraceIdFilter` 在请求进入时把 `traceId` 写入 Log4j2 `ThreadContext`、同时写入 `X-Trace-Id` 响应头；当前控制器返回值没有统一模型，也没有全局异常转换层。该模板强调中文说明性注释，并要求每个 Java 类和非简单方法说明职责与执行逻辑。

## Goals / Non-Goals

**Goals:**

- 用小而稳定的公共模型统一新接口及异常处理的响应结构。
- 复用已有链路追踪上下文，不再创建第二套请求标识机制。
- 让每种指定校验注解都出现在一个可通过 HTTP 调用和自动化测试验证的示例中。
- 通过明确的异常优先级区分客户端输入错误和服务器内部错误。

**Non-Goals:**

- 不通过返回值增强器自动包装所有既有控制器返回值，也不改变现有 `/welcome`、`/echo` 和 resilience4j 示例接口的响应契约。
- 不新增业务异常层次、国际化消息源、错误码枚举或字段级错误列表。
- 不处理认证、授权、限流等由安全或网关组件产生的非控制器异常。

## Decisions

### 1. 使用不可变泛型响应记录和静态工厂工具

`RestResult<T>` 采用 Java 记录承载 `Integer code`、`T data`、`String message`、`String traceId`、`Long timestamp`，用语言级不可变数据载体减少模板样板代码。`RestResultUtils` 作为不可实例化的静态工具类，提供有数据和无数据的成功方法，以及指定错误码、错误消息的失败方法。

成功业务码固定为 `0`，失败业务码使用对应 HTTP 状态码数值，使调用方可以分别依赖 HTTP 状态与响应体字段。工具类在每次构造时读取 `ThreadContext` 中的 `traceId`；空字符串转换为 `null`，避免非 Web 场景产生异常或伪造标识。`timestamp` 在每次构造响应时通过 `System.currentTimeMillis()` 生成，统一使用 Unix 毫秒值，便于不同语言客户端解析并避免时区歧义。

备选方案是使用 Lombok 可变对象或手写构建器，但这会引入不必要的可变状态和更多模板代码。另一个备选方案是统一返回 HTTP 200，但会削弱代理、监控和标准客户端对错误状态的识别能力。

### 2. 只显式使用统一响应，不自动改写任意控制器返回值

新增的校验示例接口显式返回 `RestResult`，全局异常处理器也显式构造 `RestResult`。不引入 `ResponseBodyAdvice` 自动包装机制，以避免重复包装、文件下载或文本响应被意外改变，也避免破坏已归档能力对应的既有示例接口契约。

备选方案是全局自动包装所有响应，虽然调用方使用简单，但需要额外定义排除规则、重复包装检测及文档模型处理，超出本次基础示例范围。

### 3. 通过校验配置定制器启用 Hibernate Validator 快速失败

新增校验配置类，通过 Spring Boot 提供的校验配置定制扩展向底层校验器设置 `hibernate.validator.fail_fast=true`，保留 Boot 对校验器、消息插值器和依赖注入的自动配置。配置类需要说明快速失败只能保证返回一个违规结果，不能保证多个非法字段之间固定的发现顺序。

备选方案是自行声明 `LocalValidatorFactoryBean`，但这会接管更多自动配置细节；仅为一个属性替换整个校验器没有必要。

### 4. 使用单一请求对象集中展示全部约束

新增校验示例请求对象，以独立字段分别承载十四种约束：空值或集合约束、整数与十进制边界、正负数、邮箱、正则格式、过去与未来时间。示例控制器提供一个带 `@Valid` 请求体的 POST 接口，在合法时原样返回已校验请求对象。

各字段使用互不冲突、便于构造合法样例的边界；`@Pattern` 使用固定的“两个大写字母加四位数字”格式，十进制字段使用 `BigDecimal`，时间字段使用 `LocalDate`。对于本身允许 `null` 的格式或数值约束，示例按需要叠加 `@NotNull`，确保遗漏字段也能演示确定的失败行为。

备选方案是为每个注解建立单独端点，但会显著增加重复代码，也不利于展示真实请求对象中组合约束的用法。

### 5. 按异常类型分层处理并保留 HTTP 语义

使用 `@RestControllerAdvice` 建立统一异常处理器，具体处理请求体字段校验、Spring MVC 方法参数校验、传统约束违规、缺少请求参数、绑定失败和请求体不可读异常，统一映射为 HTTP 400。处理器优先提取一个可理解的约束消息；若框架异常没有可用详情，则使用稳定的中文兜底提示。

最后使用通用异常处理方法返回 HTTP 500 和固定消息“服务器内部错误”，同时以错误级别记录完整异常堆栈；日志上下文已有 `traceId`，响应也由统一工具读取同一标识。具体异常处理方法先于通用处理方法匹配，避免客户端错误被误判为服务器错误。

备选方案是继承 Spring MVC 的 `ResponseEntityExceptionHandler`，但本次只需要少量明确映射，组合方式会增加继承约束和受保护方法覆盖成本。

### 6. 用无外部基础设施的测试验证契约

响应模型与工具类使用普通单元测试；快速失败通过校验器或配置上下文测试验证；控制器和异常处理使用聚焦 Web 层的 MVC 测试，覆盖合法请求、多个同时违规时仅返回一条消息、解析错误以及未预期异常。测试隔离 Nacos、MySQL 和 Redis，避免模板已有完整应用测试所需的本地基础设施影响本能力验证。

## Risks / Trade-offs

- [快速失败时首个违规字段的顺序不稳定] → 测试只断言返回一项违规，不依赖具体字段顺序；文档明确这一限制。
- [通用异常处理器可能覆盖框架后续新增的特殊异常] → 具体处理器保持精确类型匹配，并通过 HTTP 状态测试保护现有映射。
- [固定中文消息暂不支持国际化] → 本次定位为中文模板示例；未来若引入消息源，可保持响应契约不变并替换消息解析方式。
- [不自动包装既有端点意味着统一能力需要控制器主动采用] → 在示例控制器和工具类注释中说明推荐用法，避免以隐式机制换取表面一致性。

## Migration Plan

1. 先加入响应模型、构造工具及独立测试，不影响既有端点。
2. 加入校验配置、示例请求对象和示例控制器。
3. 加入全局异常处理及 Web 层测试，确认 HTTP 状态和响应体契约。
4. 执行不依赖外部基础设施的目标测试，再执行完整测试并如实记录外部服务导致的环境性失败。

回滚时可按相反顺序移除异常处理、校验示例与统一响应类；由于不修改既有接口响应，无需调用方迁移或数据回滚。
