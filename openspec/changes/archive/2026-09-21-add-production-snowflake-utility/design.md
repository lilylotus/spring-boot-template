## Context

项目使用 Java 21，`org.example.simple.util` 下已有不可实例化的静态工具类，但没有分布式 ID 生成能力。雪花算法的唯一性同时依赖进程内同步、稳定时钟以及跨实例唯一节点配置；实现不能把节点冲突风险隐藏在自动推断逻辑中。需求边界见 `proposal.md` 和增量规范。

## Goals / Non-Goals

**Goals:**

- 以单个静态入口提供低依赖、线程安全的 `long` ID。
- 明确节点分配责任，并阻止运行期切换节点配置。
- 在正常时钟、轻微回拨和序列耗尽场景中保持唯一性。
- 让关键位布局和异常路径可通过确定性测试验证。

**Non-Goals:**

- 不负责在集群中自动分配或协调节点编号。
- 不承诺跨数据中心按真实生成时间严格排序。
- 不提供数据库号段、UUID、字符串前缀或 ID 持久化能力。
- 不保证应用重启后仍记住上次时间戳；部署平台必须保证节点编号不会被仍存活的实例复用。

## Decisions

### 使用一次性显式或默认初始化

公共 API 为 `initialize(int datacenterId, int workerId)` 和 `nextId()`。静态类持有一个内部生成器；首次初始化固定节点参数，相同参数重复调用视为幂等，不同参数再次初始化抛出 `IllegalStateException`。`nextId()` 在未初始化时使用 `datacenterId = 0`、`workerId = 0` 自动初始化。

默认初始化与显式初始化使用同一把类锁，获取锁后再次检查生成器是否存在。若显式配置已先完成，`nextId()` 直接使用该生成器；若默认初始化先完成，后续显式配置只允许 `(0, 0)`。并发首次调用只能发布一个生成器，不重置序列和时间戳。通过 `volatile` 发布实例，已初始化后的发号路径无需再次获取初始化锁。

备选方案是从 MAC、IP、主机名或进程号计算节点编号，但 10 位节点空间中的哈希碰撞无法可靠检测，容器克隆与网络变化也会破坏稳定性，因此不符合生产唯一性要求。

### 采用固定 64 位布局与固定纪元

布局采用 `0 | timestamp(41) | datacenter(5) | worker(5) | sequence(12)`，移位分别为 22、17 和 12。纪元固定为 `2025-01-01T00:00:00Z`，使 ID 在约 69 年内保持正数。实现校验当前时间不早于纪元且相对时间未超过 41 位上限，避免静默截断。

备选方案是使用启动时间作为纪元，但不同进程无法互操作和解析；使用 Unix 纪元则 41 位容量已不足以覆盖当前日期，因此均不采用。

### 使用同步临界区保证状态一致性

生成器以 `synchronized` 串行更新最近时间戳和序列号。单节点上限为每毫秒 4096 个 ID，临界区仅包含读取时钟、状态判断和位运算，优先保证正确性与可审计性。

备选方案是基于 CAS 的无锁状态机，但时钟回拨与序列耗尽会显著增加状态编码和证明难度；对本工具的单节点理论容量而言，同步方案更稳健。

### 对时钟回拨采用有限等待与阈值失败

最大容忍回拨为 5 毫秒。小于等于阈值时在同步临界区内使用短暂 `LockSupport.parkNanos` 等待至最近时间戳；超过阈值立即抛出包含回拨量的中文 `IllegalStateException`。序列耗尽同样等待进入下一毫秒。等待循环检查中断标记，发生中断时保留标记并失败，避免无限自旋。

备选方案是直接沿用最后时间戳生成逻辑时间，但持续回拨可能快速耗尽序列并生成显著超前于真实时钟的 ID；任何回拨都立即失败又会放大常见的微小时钟抖动，因此采用小阈值等待。

### 内部生成器支持可控时钟测试

`SnowflakeUtils` 的公共表面保持纯静态；同一文件内使用包可见的内部生成器并接收 `LongSupplier` 时钟。生产静态实例使用 `System::currentTimeMillis`，测试直接构造内部生成器以确定性覆盖回拨、时间越界和序列耗尽，无需修改系统时钟或暴露测试专用公共 API。

## Risks / Trade-offs

- [不同实例使用默认节点组合仍会碰撞] → 默认 `(0, 0)` 仅适用于独占该节点组合的单生成器部署；多实例必须在首次发号前显式分配不同节点组合。
- [严重时钟回拨会造成短时不可用] → 快速失败并报告回拨量，交由监控告警和时钟服务修复，优先避免重复 ID。
- [同步生成在极端竞争下可能成为热点] → 单节点理论容量受 4096 ID/毫秒限制，同步开销相对可控；通过并发测试验证目标负载下的唯一性。
- [静态配置不支持同一 JVM 多租户节点] → 这是防止运行期误切换的有意约束；多节点生成需求应使用独立进程或另行设计实例化 API。
- [应用重启丢失最近时间戳] → 依赖生产环境可靠时钟，且旧实例退出前不得将同一节点号分配给新实例。

## Migration Plan

单生成器部署可直接调用 `nextId()` 使用默认节点组合；多实例接入方先在部署系统中分配唯一节点组合，在应用启动阶段调用 `initialize`，再开放业务流量。回滚时停止调用并移除工具即可，不涉及数据迁移；已经生成的 ID 仍可按固定布局解析。
