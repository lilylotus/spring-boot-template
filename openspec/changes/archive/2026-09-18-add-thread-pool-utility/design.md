## Context

项目使用 Java 21，通用工具位于 `org.example.simple.util`。当前业务可直接使用 JDK 并发包，但缺少统一的多线程任务提交入口。调用方不应感知或持有线程池，本设计需要在工具内部管理执行器并避免其阻止 JVM 退出。

## Goals / Non-Goals

**Goals:**

- 使用内部固定 4 线程执行器统一运行多线程任务。
- 将线程数和队列容量分别定义为公开常量 `DEFAULT_THREAD_COUNT = 4`、`DEFAULT_QUEUE_CAPACITY = 1024`。
- 对外提供 `Runnable` 和 `Callable<T>` 的执行或提交方法，不暴露执行器。
- 通过 `Future` 保留任务完成、返回值和异常传播语义。
- 使用容量为 1024 的有界队列限制待执行任务数量，并提供可诊断的拒绝错误。
- 使用具名守护线程，使内部执行器不会单独阻止 JVM 正常退出。

**Non-Goals:**

- 不提供线程池创建方法或 `ExecutorService` 访问器。
- 不允许调用方修改内部线程数、队列容量、拒绝策略或线程工厂。
- 不管理 Spring Bean 生命周期，也不提供关闭内部执行器的公共方法。
- 不在本次变更中增加线程优先级、动态扩缩容或监控指标配置。
- 不替换 RPC 模块已有的线程执行器。

## Decisions

### 封装单个内部执行器

新增不可实例化的 `ExecutorServiceUtils` 最终类，内部使用私有静态 `ThreadPoolExecutor`。工作线程数固定为常量 4，等待队列容量固定为常量 1024。类初始化时创建一次执行器，所有公开任务方法复用该实例，调用方无法获取或替换线程池。

未采用每次任务调用临时创建线程池的方式，因为高频任务会反复创建与销毁线程；也不返回执行器，因为这会允许调用方关闭共享资源或绕过工具类约定。

### 提供执行与提交方法

`execute(Runnable task)` 用于无需结果的异步任务，并保持 `Executor.execute` 的异常处理语义。`submit(Runnable task)` 返回 `Future<?>`，`submit(Callable<T> task)` 返回 `Future<T>`，调用方可等待完成、取得结果或观察任务异常。

所有任务参数在提交前使用 `Objects.requireNonNull` 校验，并转换为带中文说明的 `IllegalArgumentException`，统一调用方错误语义。

### 使用具名守护线程

内部线程工厂通过原子序号将线程命名为 `ExecutorServiceUtils-1` 等可识别名称，并将线程设置为守护线程。守护线程不会因为共享执行器持续存活而单独阻止 JVM 关闭，线程名称便于日志与线程转储诊断。

### 固定线程数与队列

内部直接构造 `ThreadPoolExecutor`，核心线程数和最大线程数均为 4，空闲时间为 0，任务队列使用容量为 1024 的 `ArrayBlockingQueue`。因此最多 4 个任务同时运行、1024 个任务等待；当两部分均已占满时拒绝第 1029 个未完成任务，避免任务无限堆积导致内存耗尽。

### 拒绝策略提供错误原因

使用自定义 `RejectedExecutionHandler`。队列饱和时抛出 `RejectedExecutionException`，中文消息包含“线程池任务已满”原因，以及拒绝瞬间的活动线程数、排队任务数和最大队列容量。`execute` 与两个 `submit` 重载使用同一执行器，因此共享完全相同的拒绝行为。

未使用静默丢弃或调用方运行策略，因为前者会隐藏任务丢失，后者会把执行压力传递给调用线程并改变异步语义。

## Risks / Trade-offs

- [守护线程中的任务可能在 JVM 退出时未完成] → 在 Javadoc 中说明重要任务必须由调用方通过返回的 `Future` 等待完成。
- [容量 1024 可能不适合所有业务峰值] → 使用公开常量记录容量，并在拒绝异常中提供实时状态；不同容量需求使用专用执行器。
- [拒绝瞬间的线程池状态具有并发变化] → 异常数据用于诊断而非精确计费，测试只断言原因与关键字段存在。
- [共享执行器中的长时间阻塞任务会影响其他调用方] → 明确该工具适合常规异步任务，隔离要求较高的业务使用专用执行器。

## Migration Plan

1. 新增工具类和单元测试，不修改现有调用方。
2. 运行多线程任务专项测试和完整构建。
3. 如需回滚，删除新增类、测试及对应规范即可，现有功能不受影响。
