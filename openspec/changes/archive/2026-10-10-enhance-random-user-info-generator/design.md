# Design

## Context

见 proposal.md 的 Why。补充三条约束，它们直接决定了下面的取舍：

- **类文件常量池上限**：单个 `String` 常量在 class 文件中以 modified UTF-8 存储，长度上限 65535 字节。`area-codes.csv` 共 2842 行、111179 个字符，UTF-8 约 110 KB，无法放进一个字符串常量。
- **方法字节码上限**：单个方法的 `Code` 属性上限 64 KB，因此"用 `String[]` 数组字面量逐条列出 2842 个元素"会让 `<clinit>` 直接超限，不可行。
- **用户已确认的两个前提**：`src/main/resources/area-codes.csv` 原样保留（不删、不移动）；少数民族姓名采用"固定完整姓名池整条抽取"，不做姓氏与名字的拼接组合。

## Goals / Non-Goals

**Goals:**

- `RandomUserInfoUtils` 的类加载路径上不出现任何 I/O：把 `RandomUserInfoUtils.java` 单个文件拷到别的工程即可直接编译运行。
- 内置地区码表与仓库里保留的 `area-codes.csv` 快照之间，有自动化手段保证不漂移。
- 姓名生成在"长度恒为 2~4"的硬约束下，覆盖汉族单姓、汉族复姓、少数民族三类。

**Non-Goals:**

- 不做地区码表的自动更新、增量同步或构建期代码生成（Gradle 任务 / annotation processor）。本次内置的是一次性静态快照。
- 不改变 `generateNames` / `generateIdCardNos` / `generatePhoneNumbers` / `generateRegions` / `generateUsers` 的签名与唯一性语义。
- 不对少数民族姓名做民族归属标注，也不提供"按民族筛选"的 API。
- 不追求姓名各类别之间符合真实人口统计分布。

## Decisions

### 决策 1：地区码表用 3 个文本块（text block）常量内置，类加载时解析一次

把 CSV 按 1000 行切成 3 段，每段写成一个 `private static final String` 文本块常量（`AREA_CODES_CSV_PART_1` ~ `_PART_3`）。各段 UTF-8 实测为 37544 / 36740 / 36895 字节，最大一段约 37 KB，距 65535 字节上限留出充足余量。`parseAreaCodes()` 依次按行切分三段文本、以第一个逗号拆成 `code` 与 `region`，产出不可变 `List<AreaCode>`，赋给原有的 `AREA_CODES` 常量。

文本块内容整体缩进与结尾 `"""` 对齐，由编译器剥离附带缩进（incidental whitespace），因此解析逻辑无需 `trim`，也不违反 `.editorconfig` 的 `trim_trailing_whitespace`。CSV 每行形如 `110101,北京市东城区`，不含引号、转义或内嵌逗号，`indexOf(',')` 的朴素拆分足够；仍保留"逗号缺失则跳过该行"的防御分支，避免源码被误编辑后产生越界异常。

考虑过的替代方案：

- **`String[]` 数组字面量逐条列出**：`<clinit>` 字节码超 64 KB 上限，不可行。
- **源码中逐条 `areaCodes.add(new AreaCode("110101", "北京市东城区"))`**：数据能进编译期类型检查、也不需要解析代码，但 2842 条 add 约 57 KB 字节码，距 64 KB 硬上限余量过薄，必须再拆成多个 append 方法；且源码从约 115 KB 涨到约 230 KB。收益不足以抵消体积与结构代价，放弃。
- **构建期从 CSV 生成 Java 源码**：能彻底消除双份数据，但引入 Gradle 代码生成任务，与"单文件可独立拷走"的目标相悖（拷走的文件变成生成产物），复杂度不划算。
- **Base64 / GZIP 后内置**：字节数更小，但源码不可读、不可 review、diff 无意义，且解压需要额外代码，不划算。
- **保留 classpath 读取 + 找不到资源时回退到内置表**：两条加载路径都要测，且"到底用了哪份数据"变得不可预测，放弃。

### 决策 2：`area-codes.csv` 降级为"数据来源 + 测试黄金文件"，并新增漂移测试

生产代码不再读取该文件，但文件保留在 `src/main/resources` 下（用户已确认）。为避免内置表与 CSV 悄悄不一致，新增测试 `builtInAreaCodeTableMatchesCsvSnapshot()`：从 classpath 读 CSV 构造 `code -> region` 映射，与内置表逐条比对条数与映射关系。

内置表本身不对外暴露（`AREA_CODES` 与 `AreaCode` 保持私有），测试通过已有的公开行为间接取得全量内置数据：`generateRegions(2842)` 无放回返回全部地区名称，可校验"条数一致 + 名称集合一致"；`generateUsers` 的 `region` 与 `idCardNo` 前 6 位的对应关系校验（已有测试）覆盖"码 -> 名称"的映射正确性。这样既不为测试开放内部 API，也不让测试自我循环（CSV 是独立参照）。

考虑过的替代方案：把 `parseAreaCodes()` 或 `AREA_CODES` 放宽到包可见以便测试直读——会把内部实现钉进可见性契约，而现有公开行为已足够覆盖，放弃。

### 决策 3：姓名生成改为三分支策略，长度约束由各分支自身保证

`buildRandomName()` 按权重随机选一个分支，每个分支都只能产出 2~4 字：

- **汉族单姓（权重 70）**：1 字姓 + 1~3 字名 → 总长 2~4。
- **汉族复姓（权重 10）**：2 字复姓 + 1~2 字名 → 总长 3~4。
- **少数民族（权重 20）**：从 `MINORITY_NAMES` 整条抽取，池内每条本身就是 2~4 字。

权重用一个 `int` 累积区间比较实现（`random.nextInt(100)` 落在 `[0,70) / [70,80) / [80,100)`），不引入额外依赖。"长度 2~4"由三个分支分别保证，而不是"先生成再按长度过滤"——过滤式实现会在边界上浪费随机尝试，也让 `MAX_ATTEMPTS_PER_ELEMENT` 的语义变模糊。

权重取值的理由：少数民族姓名池是固定枚举（约 100 条），组合空间远小于汉族分支，权重给到 20 已能让"足够大样本下必然出现少数民族姓名"稳定成立，再高则会显著拉高整体重复率、挤压 `generateNames` 的可用唯一空间。复姓给 10 是因为复姓在真实人口中本就稀少，给高了反而不像真实数据。

考虑过的替代方案：三类等概率（各 1/3）——少数民族池只有约 100 条，等概率下 `generateNames(1000)` 会在该分支上频繁撞重复、触发大量重试，唯一空间被不必要地收紧。

### 决策 4：少数民族姓名用固定完整姓名池

内置约 100 条真实常见的 2~4 字少数民族姓名（蒙古族、维吾尔族、藏族、哈萨克族、彝族、回族、朝鲜族等），整条抽取。相比"民族姓氏池 + 名字用字池"拼接，整条抽取不会拼出"看着像但实际不存在"的名字，长度也天然落在 2~4。代价是该分支组合空间固定（约 100），由决策 3 的权重设计消化。

池内只放不含 `·` 分隔符的姓名形式（如 `买买提`、`阿依古丽`、`巴特尔`、`次仁卓玛`），不收录 `阿卜杜拉·买买提` 这类带分隔符的写法——既是为了守住"2~4 字且只含汉字"的约束，也因为多数业务系统的姓名字段不接受分隔符。

### 决策 5：`GIVEN_NAME_CHARS` 扩充到 200 字，保持单一扁平数组

直接在现有 100 字后追加 100 个常见取名用字（去重，不与原有 100 字重叠），仍是一个扁平 `String[]`。新增字按"常见、性别中性或两性均用、确实用于取名"筛选，不引入生僻字。

扩充后汉族单姓分支的组合空间从 `100 × (100 + 100²) ≈ 1.01e6` 升到 `100 × (200 + 200² + 200³) ≈ 8.04e8`，`generateNames(1000)` 的重试压力大幅下降，`MAX_ATTEMPTS_PER_ELEMENT = 1000` 的现有上限无需调整。

不按性别/寓意分池：会改变 API 形态和随机语义，超出本次范围。

## Risks / Trade-offs

- **内置表与 CSV 两份数据可能漂移** → 决策 2 的漂移测试在每次 `./gradlew test` 时逐条比对，不一致即测试失败。
- **源码文件膨胀到约 115 KB，IDE/diff 体验变差** → 三个文本块常量集中放在类的末尾、上方加注释说明"机器生成的静态快照，不要手工编辑，需更新请重新从 `area-codes.csv` 生成"，把噪音隔离在一处。
- **类加载时解析 2842 行有一次性开销** → 只在 `RandomUserInfoUtils` 首次被触达时执行一次，量级在毫秒内，且比原先的 classpath I/O 更快（无 `InputStream` 打开/读取）。
- **少数民族姓名分支组合空间仅约 100 条，大批量生成时该分支重复率高** → 由决策 3 的权重（20%）与 `generateUniqueName` 的重试机制吸收；极端大 `count` 下仍由既有的 `IllegalStateException` 兜底，不会死循环。
- **少数民族姓名池的"真实性"依赖人工挑选，可能带入拼写或族属上的不准确** → 只收录广为人知的常见名；本工具的用途是测试数据生成，不作为民族语言学参考，Javadoc 中明示这一点。
- **姓名长度从 2~3 扩到 2~4，下游若有写死的长度断言会失败** → 属于本次有意的行为变更，已在 spec delta 的 MODIFIED 要求中声明；仓库内无此类断言。

## Migration Plan

无需迁移：公开方法签名与返回类型不变，调用方代码无需改动，`area-codes.csv` 位置与内容不变。唯一的行为变更是随机姓名的长度区间与取值范围扩大（见 spec delta）。回滚方式为 `git revert` 该提交。
