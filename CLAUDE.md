## Project

Spring Cloud Gateway template service (`cn.nihility.gw`, artifact `CloudGateway`). Java 21, Spring Boot 3.5.16, Spring Cloud 2025.0.3, Gradle (Groovy DSL). Single module, no submodules.

```powershell
./gradlew build                 # compile + test + package
```

## Logging (Log4j2)

Logging runs on **Log4j2, not Logback**. Two pieces make that work, and both are load-bearing:

1. `build.gradle` globally excludes `spring-boot-starter-logging` via `configurations.configureEach`. Without it, `spring-boot-starter-web`/`webflux`/nacos drag in Logback plus `log4j-to-slf4j`, and startup dies with `log4j-slf4j2-impl cannot be present with log4j-to-slf4j`. Do not remove that block.
2. `src/main/resources/log4j2-spring.xml` — named `-spring` so Spring Boot's `LoggingSystem` loads it and `logging.level.*` / `logging.file.path` keep working.

Async logging uses `<AsyncLogger>`/`<AsyncRoot>` backed by `com.lmax:disruptor:4.0.0`. Because async is on, `includeLocation="false"` is set: **if you add `%L`, `%M`, `%C` or `%l` to a pattern you must flip that to `true`**, or location will print as `?`.

Files land in `logs/` (override with `logging.file.path`; the XML reads the `LOG_PATH` system property Spring Boot sets):

- `logs/CloudGateway.log` — everything at root level, archived to `logs/archive/app/`
- `logs/CloudGateway-error.log` — ERROR only, archived to `logs/archive/error/`

Retention knobs live in the `<Properties>` block at the top of the XML: 200MB per file, roll daily or on size, 5 files per day (`DefaultRolloverStrategy max`), 7-day age limit and a 35-file total cap (the `<Delete>` action). The two appenders archive into **separate** subdirectories on purpose — each `<Delete>` is scoped by `basePath`, so the 35-file cap applies per appender and the globs stay unambiguous.

`logs/` is gitignored and is regenerated by any test run. `%15.15t` truncates thread names from the left, so `boundedElastic-1` prints as `oundedElastic-1` — that is the pattern, not a bug. Patterns carry `%notEmpty{[%X{traceId}] }` so startup lines (which have no traceId) don't render empty brackets.

## Request tracing (traceId + access timing)

`cn.nihility.gw.trace` implements correlation-id tracing. `TraceFilter` is a `WebFilter` ordered `HIGHEST_PRECEDENCE`, so traceId exists before any other filter or the gateway's routing filters.

Per request it reuses the inbound `X-Trace-Id` (or mints a 32-hex one), mutates the *request* headers so the gateway forwards it downstream, echoes it on the response, and logs on `doFinally`:

```
2026-09-22 00:24:51.735  INFO [flux-http-nio-2] [testtraceid0123456789abcdef01234] c.n.g.t.TraceFilter : GET /welcome cost [6]ms
```

`doFinally` is used rather than `then(...)` because it fires on completion, error **and** cancellation — a client that disconnects mid-request still gets a timing line.

### Why MDC alone is not enough here

WebFlux moves one request across several threads, so MDC (a ThreadLocal) cannot hold traceId on its own. The real carrier is the **Reactor Context** (`contextWrite(Context.of(TraceContext.TRACE_ID, traceId))`), bridged back into MDC by:

- `TraceIdThreadLocalAccessor` — an `io.micrometer.context.ThreadLocalAccessor` keyed on `traceId` that reads/writes MDC. This requires the `io.micrometer:context-propagation` dependency; it is **not** pulled in transitively.
- `Hooks.enableAutomaticContextPropagation()` in `TraceConfiguration` — makes Reactor restore the MDC around operator execution on whichever thread runs it. Both are done once per JVM behind an `AtomicBoolean`, since the hook is global and tests build several contexts.

Without both pieces, traceId sits in the Reactor Context and ordinary `log.info` calls in business code print nothing for `%X{traceId}`.

`TraceFilter.logCost` still binds the traceId explicitly via `TraceContext.runWith(...)`, because a `doFinally` callback is not guaranteed to have the ThreadLocal restored (notably on cancellation).

### Cross-thread propagation outside Reactor

For plain thread pools the Reactor machinery does not apply:

- **Thread pools** — `TraceTaskDecorator` (a `TaskDecorator` bean, auto-wired into `applicationTaskExecutor`, so `@Async` works) and `TraceExecutors.wrap(...)` for hand-rolled pools. Both snapshot MDC on the submitting thread and **restore the worker's previous context in a `finally`** — pooled threads are reused, so skipping the restore leaks one request's traceId into the next task.
- **Ad-hoc child threads** — `log4j2.component.properties` sets `log4j2.isThreadContextMapInheritable=true`. This only helps threads *created* under a request and is the wrong tool for pools, which is why the wrappers exist.

`TraceFilterTest` asserts all of this end-to-end against the real log file, which also proves the async appender flushed.

## OpenFeign

`FeignConfiguration` carries `@EnableFeignClients(basePackages = "cn.nihility.gw")` and the tracing interceptor. All tuning is in `application.yaml` under `spring.cloud.openfeign`:

- `httpclient.hc5.enabled: true` — Apache HttpClient 5 (`feign-hc5`) instead of Feign's default `HttpURLConnection`, which has no connection pool. Pool size is `max-connections` / `max-connections-per-route`.
- `client.config.default.connect-timeout: 3000` and `read-timeout: 5000` — `default` is the fallback for every client; override per client by its `@FeignClient` name.

Because this is a **reactive** app, `FeignConfiguration` must also declare an `HttpMessageConverters` bean: `HttpMessageConvertersAutoConfiguration` carries a `NotReactiveWebApplicationCondition`, so it backs off in a WebFlux app and Feign's `SpringDecoder` fails at call time with `No qualifying bean of type 'HttpMessageConverters'`. The bean is `@ConditionalOnMissingBean`, so it steps aside if a servlet stack is ever added back.

**Feign is blocking, and this is a reactive app.** Never call a `@FeignClient` directly from a handler — it stalls a Netty event-loop thread. `FeignService` is the pattern to copy:

```java
return Mono.fromCallable(() -> { log.info(message); return call.get(); })
        .subscribeOn(Schedulers.boundedElastic());
```

`fromCallable`, not `just`: `Mono.just(client.welcome())` evaluates the blocking call at assembly time, on the event loop, which defeats the whole point. The resulting thread hop is visible in the logs and traceId rides along:

```
INFO [flux-http-nio-2] [welcometraceid...] c.n.g.c.WelcomeController : Controller feign /welcome call
INFO [oundedElastic-1] [welcometraceid...] c.n.g.s.FeignService      : feign /welcome call
```

traceId survives that hop because of `Hooks.enableAutomaticContextPropagation()` (see the tracing section) — it covers `subscribeOn`/`publishOn` boundaries. `WelcomeControllerTest` asserts both the `boundedElastic` thread and the traceId from inside a stubbed client, rather than parsing logs.

Controllers return `Mono<...>`; side effects like logging belong in `Mono.fromSupplier(...)` or `.doFirst(...)` so they run at subscription rather than assembly.

`traceIdRequestInterceptor` copies the current MDC traceId onto every outgoing Feign request. Two details matter: it skips the header when the client method already declares it (case-insensitively, so an explicit `x-trace-id` isn't duplicated), and it reads MDC on the *calling* thread — Feign is synchronous, so a call made from a pool needs `TraceExecutors.wrap(...)` first or there will be no traceId to copy. A plain `RequestInterceptor` `@Bean` in the main context applies to all clients; it does not need to be listed in a per-client configuration class.

With this in place the traceId now survives both hops: gateway-proxied requests (via the `TraceFilter` request wrapper) and gateway-originated Feign calls.

### Gotchas when adding Feign clients

`@EnableFeignClients` scans `cn.nihility.gw`, which **includes test classes**. A `@FeignClient` defined in test sources is registered into every application context, so give its `url` a resolvable default (`url = "${trace.probe.url:http://localhost:1}"`) or non-web test contexts will fail to start.

Do not point a `@FeignClient` `url` at `${local.server.port}`. `FeignClientFactoryBean` resolves the URL during bean creation, but `local.server.port` is only published in `finishRefresh()`, so the placeholder arrives unresolved and the context dies with `... is malformed`. `FeignTraceTest` works around this by reserving a free port in a static initializer and running with `DEFINED_PORT`.

`FeignTraceTest` asserts the client unwraps to `ApacheHttp5Client` (it is wrapped by `FeignBlockingLoadBalancerClient` because spring-cloud-loadbalancer is on the classpath), that the traceId reaches the downstream endpoint, that the YAML timeouts are actually bound, and that a slow downstream fails at ~5s.

## Build configuration

Version numbers and the JDK path live in `gradle.properties`, **not** in `build.gradle` — change them there:

- `SpringBootVersion`, `SpringCloudVersion`, `CloudAliNacosVersion`, `JacksonVersion`
- `org.gradle.java.home=C:/kits/Java/jdk-21.0.1` — a hard-coded absolute path. On a machine without that JDK, override it rather than editing the file in a commit.

Repositories are mirrored for China networks: Aliyun is listed before Maven Central in `build.gradle`, and the Gradle distribution in `gradle/wrapper/gradle-wrapper.properties` comes from a Tencent mirror. Keep the mirrors first when editing.

`compileJava`/`compileTestJava`/`javadoc` are pinned to UTF-8 because non-ASCII (Chinese) comments otherwise break compilation on Windows' default codepage. Do not remove those settings.

## Architecture

**Reactive gateway on Netty.** The dependency is `spring-cloud-starter-gateway` (the reactive/WebFlux gateway) plus `spring-boot-starter-webflux`; there is no servlet API on the classpath at all. Write filters as `WebFilter`/`GlobalFilter` returning `Mono`, never `jakarta.servlet.Filter` — servlet types will not compile here.

Note the declared `spring-cloud-starter-gateway:3.1.10` version is **not** what gets used: the `spring-cloud-dependencies:2025.0.3` BOM overrides explicitly declared versions, so it resolves to `4.3.5` (`./gradlew dependencies` shows `3.1.10 -> 4.3.5`). This is fortunate — gateway 3.1.x targets Boot 2.6/`javax` and cannot run on Boot 3.5.16. To actually pin 3.1.x you would have to drop the BOM and downgrade Boot, which is not viable on Java 21 here.

**Configuration lives in Nacos, not in this repo.** `src/main/resources/application.yaml` holds only the bootstrap essentials (port, app name, Nacos address `10.10.88.31:8848`, active profile `prod`) and then imports:

```yaml
spring.config.import:
  - optional:nacos:CloudGateway.yml
  - optional:nacos:CloudGateway-prod.yml
```

Later entries win, so the profile-specific data-id overrides the shared one, and both override `application.yaml`. **Route definitions are expected to come from Nacos** — an empty local config with no routes is normal. The `optional:` prefix means startup succeeds when Nacos is unreachable, so a locally-running gateway with no routes usually means Nacos was not reached, not that config is missing. Nacos discovery is enabled, and `spring.cloud.inetutils.preferredNetworks: 10.` forces registration on the `10.x` network interface.

`CloudGatewayApplication` is a bare `@SpringBootApplication` with no custom beans yet; the test is an empty `@SpringBootTest` context-load check.

## Conventions

- `.editorconfig` is authoritative: UTF-8, LF, 4-space indent, final newline, trailing whitespace trimmed; Java max line length 120; YAML 2-space; `.bat`/`.cmd` keep CRLF; Markdown uses tabs and preserves trailing whitespace. Note `build.gradle` itself is tab-indented — match the surrounding file when editing it.
- Commits use Conventional Commits with a scope, e.g. `feat(gateway): gateway init`.
- Work branches off `develop` (PR base). The current branch is `cloud-gateway-3.1.x`; sibling branches (`3.5.x`, `java-template`, `flowable-template`) are separate template variants, not feature branches.
