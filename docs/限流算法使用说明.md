# 限流算法使用说明

`org.example.simple.rate` 包提供五种常见限流算法，统一实现 `RateLimiter` 接口，仅依赖 JDK。

## 接口约定

```java
public interface RateLimiter {
    default boolean tryAcquire();          // 获取 1 个许可
    boolean tryAcquire(int permits);       // 一次性获取多个许可，全有或全无
}
```

- 非阻塞：立即返回是否放行，不等待。需要等待时由调用方自行重试或排队。
- `permits <= 0` 抛出 `IllegalArgumentException`；`permits` 超过窗口上限或桶容量时永远无法满足，直接返回 `false`。
- 获取失败不产生副作用（不计数、不注水、不扣令牌）。
- 线程安全；时间基于单调时钟 `System.nanoTime()`，不受系统时间调整影响。
- 构造参数非法（上限、容量、子窗口数非正，速率非有限正数，窗口非正）抛出 `IllegalArgumentException`，窗口为 `null` 抛出 `NullPointerException`。

## 使用示例

```java
// 固定窗口：每分钟最多 100 次
RateLimiter fixed = new FixedWindowRateLimiter(100, Duration.ofMinutes(1));

// 滑动窗口（日志法）：任意 10 秒内最多 5 次，精确
RateLimiter log = new SlidingWindowLogRateLimiter(5, Duration.ofSeconds(10));

// 滑动窗口计数：每秒最多 1000 次，划分为 20 个 50 毫秒的子窗口
RateLimiter counter = new SlidingWindowCounterRateLimiter(1000, Duration.ofSeconds(1), 20);

// 漏桶：最多积压 50，每秒漏出 200
RateLimiter leaky = new LeakyBucketRateLimiter(50, 200.0);

// 令牌桶：容量 100（允许突发 100），每秒补充 500 个令牌
RateLimiter token = new TokenBucketRateLimiter(100, 500.0);

if (token.tryAcquire()) {
    handle(request);
} else {
    reject(request);   // 如返回 HTTP 429
}
```

## 算法对比

| 实现 | 原理 | 精度 / 突发 | 每次判断 | 内存 |
| --- | --- | --- | --- | --- |
| `FixedWindowRateLimiter` | 固定窗口内计数，越过窗口边界清零（窗口与创建时刻对齐） | 窗口边界两侧短时间内可放行 2 倍上限 | O(1) | O(1) |
| `SlidingWindowLogRateLimiter` | 记录每次放行的时间戳与许可数，统计 `(now - window, now]` 内的总数 | 精确，任意窗口内不超过上限 | 均摊 O(1) | O(limit) |
| `SlidingWindowCounterRateLimiter` | 窗口划分为 `buckets` 个子窗口（默认 10），累加最近 `buckets` 个子窗口的计数 | 近似，误差约为一个子窗口内的放行量；`buckets = 1` 等同固定窗口 | O(buckets) | O(buckets) |
| `LeakyBucketRateLimiter` | 水位法：每个许可注入一单位水，桶以恒定速率漏水，水位超过容量即拒绝；初始空桶 | 瞬时突发不超过容量，长期速率不超过漏水速率 | O(1) | O(1) |
| `TokenBucketRateLimiter` | 以恒定速率惰性补充令牌，每个许可消耗一个令牌；初始满桶 | 瞬时突发不超过容量，长期速率不超过补充速率 | O(1) | O(1) |

## 选型建议

- **简单计数、对精度不敏感**（如"每分钟最多发 N 条短信"）：`FixedWindowRateLimiter`。
- **上限较小、必须严格不超限**（如登录失败次数）：`SlidingWindowLogRateLimiter`。上限达到百万级时内存开销明显，改用滑动窗口计数。
- **上限较大、需要平滑限制**（如接口 QPS）：`SlidingWindowCounterRateLimiter`，子窗口越多越精确。
- **限制平均速率并容忍短时突发**（如 API 网关）：`TokenBucketRateLimiter`。
- **保护处理能力恒定的下游**：`LeakyBucketRateLimiter`，容量设为 1 时近似严格匀速。

## 注意事项

- 滑动窗口计数要求窗口纳秒数能被子窗口数整除，否则抛出 `IllegalArgumentException`；默认 10 个子窗口时，窗口应为 10 纳秒的整数倍（常见的秒、毫秒窗口均满足）。
- 水位法漏桶与初始满桶的令牌桶在数学上等价（水位 = 容量 - 令牌数），对相同请求序列的判断结果完全一致；二者的区别在于视角与扩展方向。漏桶的"排队整形"形态（请求入队、以恒定间隔出队执行）不在本包范围内。
- 漏桶与令牌桶使用浮点数记录水位与令牌，比较时带 `1e-9` 容差，小数速率（如 0.1/秒）下也能按时放行。
- 所有实现用对象锁保证线程安全；单个限流器成为极高并发下的热点时，可按用户、接口等维度分片为多个限流器。

## 不在范围内

- 阻塞式 `acquire()` 与带超时的获取。
- 漏桶的排队整形形态。
- 分布式限流（如基于 Redis）、按键分组限流、运行时动态调整参数、预热（warm-up）。
- RPC 服务端内部的令牌桶限流保持原实现，未改用本包。
