# echo_server 问题与修复记录

本文记录 `echo_server.cpp` 在高连接数压测和代码审查中发现的问题、修复方式和验证结果。

## 概览

| # | 问题 | 影响 | 状态 |
|---|---|---|---|
| 1 | fd 耗尽时，预留 fd 被其他 worker 抢走 | worker 空转占满 CPU | 已修复 |
| 2 | 超出 fd 上限的连接得不到处理 | 客户端已连上，但一直等不到回显 | 已修复 |
| 3 | 没有忽略 SIGPIPE | stdout 管道关闭后，写日志会杀掉进程 | 已修复 |
| 4 | 建连高峰期延迟升到约 2.4 秒 | 建连期间回显变慢 | 未定位，服务端程序的可能性较小 |

## 问题 1：fd 耗尽时 worker 空转

### 现象

fd 上限为 1024 时，所有 worker 的 CPU 都接近 100%，预留 fd 全部丢失。

### 原因

`shedConnection()` 的做法是：先关闭预留的 `spare_fd_` 腾出一个 fd，用它 accept 新连接并立即关闭，再重新打开预留 fd。但 fd 表由整个进程共享，所以会发生竞争：

1. worker A 关闭 `spare_fd_`，腾出一个 fd 号。
2. worker B 的 `accept4` 抢先拿走这个 fd 号。
3. worker A 的 `accept4` 仍然返回 `EMFILE`，重新打开预留 fd 也失败，`spare_fd_` 变成 -1。
4. worker A 监听队列里的连接取不出来。监听 socket 是水平触发，会持续报告可读，`epoll_wait` 每次立即返回，线程因此空转。

### 修复

fd 耗尽且无法丢弃连接时，暂停监听，之后再恢复：

- **暂停：** 用 `EPOLL_CTL_MOD` 把监听 socket 的事件设为 0，避免水平触发空转。
- **恢复：** 本 worker 关闭连接时立即恢复，否则 100ms（`kAcceptRetryMs`）后恢复。
- **重试判断：** 每轮事件循环结束时都检查时间。繁忙的 worker 可能一直等不到 `epoll_wait` 超时，所以不能只靠 `count == 0` 判断，否则其他 worker 释放了 fd，它也恢复不了。
- **预留 fd：** `spare_fd_` 为 -1 时不再调用 `close`。

```cpp
if (!shed && (accept_errno == EMFILE || accept_errno == ENFILE)) pauseAccept();

// run() 中，每轮事件循环结束时：
if (accept_paused_ && std::chrono::steady_clock::now() >= accept_retry_at_) {
    resumeAccept();
}
```

## 问题 2：多余的连接一直挂起

### 现象

TCP 握手由内核完成，所以连接即使没有被服务端 accept，客户端也认为已连上。问题 1 修复后不再空转，但 fd 耗尽时仍有约 750～790 个连接堆在监听队列里，等不到回显。

### 原因

只要 fd 真的耗尽，就要靠预留 fd 才能拒绝连接，而问题 1 的竞争无法完全避免。

### 修复

增加全局连接数上限 `ConnectionLimit`，让进程不会走到 fd 耗尽：

```
上限 = fd 软上限 - 16 - 5 × worker 数
```

- **每个 worker 预留 5 个 fd：** 监听 socket、epoll、eventfd、预留 fd 各 1 个，再加 1 个用于暂存刚 accept 的连接。
- **固定预留 16 个 fd：** 留给标准输入输出和从父进程继承的 fd。
- **超过上限：** accept 后立即关闭，并记录 `connection limit reached` 日志。
- **计数方式：** 多个 worker 共用一个原子计数器，连接关闭时归还名额。
- **启动检查：** 算出的上限不足 1 时，启动报错并退出。
- **启动输出：** 启动时打印实际上限。

```cpp
if (!limit_.tryAcquire()) {
    close(fd);
    logger_.log("connection limit reached: rejected a connection from " + peerName(addr));
    continue;
}
```

问题 1 的暂停和恢复逻辑保留，用于处理系统级 fd 耗尽（`ENFILE`）和继承了大量 fd 的情况。

## 问题 3：SIGPIPE 杀掉进程

### 现象

stdout 是管道且读端已关闭时（例如 `./echo_server | head -1`），服务端下一次写日志就会退出，退出码对应 SIGPIPE。

### 原因

socket 写入已使用 `MSG_NOSIGNAL`，但日志是用 `write` 写到 stdout 的，不受这个标志保护。

### 修复

在 `main` 开头忽略该信号。之后写日志只会失败，不影响服务：

```cpp
signal(SIGPIPE, SIG_IGN);
```

## 验证结果

以下测试都在本机回环上进行。fd 耗尽测试的条件是：fd 上限 1024、4 个 worker、2000 个客户端。

| 指标 | 修复前 | 修复问题 1 后 | 再加连接数上限后 |
|---|---|---|---|
| 正常回显的连接 | 约 1000 | 约 1000 | 988 |
| 被断开的连接 | 4～236 | 201～249 | 1012 |
| 已连上但等不到回显 | 约 750～990 | 约 750～790 | 0 |
| 每个 worker 的 CPU | 93～99% | 0～2% | 0～2% |
| 预留 fd 剩余 | 0 | 1 | 4 |
| 占用 fd | 1024（耗尽） | 1024（耗尽） | 1007 |
| 等待队列堆积（每个 worker） | 约 110～390 | 3 个 worker 约 200～320 | 0 |

加上连接数上限后，其他测试的结果如下：

| 测试 | 结果 |
|---|---|
| 连续三轮占满再全部断开 | 每轮都恢复到 988 个在线，没有名额泄漏 |
| fd 上限设为 30 | 启动报错，退出码 1 |
| 20 万 fd 上限，10000 个连接，每秒建连 900 个 | 全部在线，无错误，平均延迟约 0.6ms |
| 关闭 stdout 管道后发请求 | 进程存活，回显正常 |
| 压测后发送 SIGTERM | 正常退出，退出码 0 |

未覆盖的部分：

- 没有实际触发系统级 fd 耗尽（`ENFILE`）。
- 上述结果没有经过 Windows 压测机和真实网络。

## 使用注意

- **压高连接数前要调高 fd 软上限：** 默认 1024 时，4 个 worker 最多只能有 988 个连接。

  ```bash
  ulimit -n 20000
  ./echo_server -q
  ```

- **确认实际上限：** 启动时会打印，例如 `with 4 worker(s), max 988 connections`。
- **被拒绝时的表现：** 客户端会先连接成功，然后马上被断开，压测工具可能把它计为“被动断开”。
- **上限不能手动指定：** 目前只按 fd 上限自动计算。
- **压测时加 `-q`：** 服务端默认逐条记录日志，并持全局锁写 stdout。输出到慢终端时可能影响结果。

## 待处理

### 建连高峰期的延迟（问题 4）

在 Windows 压测机上跑 10000 个连接时，建连第 8～11 秒的延迟最高约 2.4 秒，全部连上后降回几毫秒。原因尚未定位，已知的情况是：

- `acceptAll()` 会循环 accept 到 `EAGAIN`，并不是每次只取一个。
- 本机回环以相近的节奏（每秒 900 个）建连，未能复现：等待队列最多 3 个，没有溢出，建连期间最高延迟不超过 57ms。
- 稳定期的请求量和日志量都更大，延迟却只有几毫秒。因此延迟不太可能来自回显路径或日志。
- 本机不限速建连时，延迟也会升到约 285ms，同时客户端事件循环卡顿约 300ms。说明压测端自身也能造成类似现象。

下一步需要在实际压测链路上运行以下命令，压测前后各看一次：

```bash
nstat -az TcpExtListenOverflows TcpExtListenDrops TcpExtTCPSynRetrans TcpRetransSegs
```

然后用 `--connect-rate=500` 和服务端 `-q` 各跑一轮对比：

| 观察结果 | 问题大概率在 |
|---|---|
| 溢出计数增长 | 服务端的等待队列或 accept |
| 溢出计数不变，重传计数明显增长 | 网络链路或中间设备 |
| 两者都不变，延迟仍有尖峰 | Windows 压测机 |

### 尚未实施的建议

- **空闲连接清理：** 客户端断电或断网后，连接会一直占用 fd 和连接名额。如需长期运行，建议加 `SO_KEEPALIVE` 或空闲超时。
- **调大 `somaxconn`：** 本机测试中队列没有接近上限，暂不需要。如果实际链路上出现溢出，再调整。
